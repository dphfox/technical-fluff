# Components won; only tokens still cascade

The research supports the core of the thesis but forces two corrections and one large concession. The strongest evidence is historical and institutional: Håkon Lie's own 1994 proposal and 2005 thesis define style sheets as a *negotiation between three parties who never meet* (author, reader, browser) over a document whose device and reader are unknown, and Lie himself concluded in 2005 that "Cascading is an ambitious mechanism that has failed to provide users an equal right to influence document presentations" ([Lie thesis](https://www.wiumlie.no/2006/phd/)). Every mainstream web styling tool since 2014 scoped selectors to the component, and every large migration write-up (Meta, GitHub, Linear, Atlassian) kept exactly one thing in the global cascade: a token layer as custom properties ([Meta](https://engineering.fb.com/2025/11/11/web/stylex-a-styling-library-for-css-at-scale/), [GitHub](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)). Native toolkits (SwiftUI, Compose, Flutter, Godot, Unreal, ImGui) never had selector cascades at all, and the three that imported CSS wholesale (Qt, JavaFX, GTK) ended up disowning the sheet as a theming API and sanctioning named variables instead. Server-driven UI at Netflix, Yelp, Airbnb and Spotify sends enumerated component types and semantic variants, never raw styling, and Netflix's 2026 slogan "Server decides WHAT, Client decides HOW" is the thesis in a company's own words ([Netflix](https://hosted-files.sched.co/graphqlconf2026/cb/Screens%20on%20Shuffle.pdf)). The corrections: first, the founding "unknown" of CSS was the *reader and device*, not the content, and CSS Zen Garden demonstrates *known* content under unknown style, so the post's framing of claim 2 needs tightening. Second, the honest form of claim 3 is "nothing selector-driven is worth cascading," because every encapsulation system (Shadow DOM, React Native, StyleX, Svelte, Angular) explicitly preserves inherited text properties and custom properties, and StyleX calls inheritance "the only form of style-at-a-distance" it allows ([StyleX](https://stylexjs.com/docs/learn/thinking-in-stylex/)). The concession: the cascade's user tier (user style sheets, forced-colors, reader modes, WCAG 1.4.12 text spacing) is a real accessibility mechanism that components cannot replace, and the thesis holds cleanly only on platforms like Roblox that have no user tier. Roblox's own StyleSheets, shipped May 2025 to July 2026, are the live counterexample, but the community praise clusters almost entirely on tokens, themes and the declarative state/responsive/transition features the engine previously lacked, and the system's own rules ("Overrides apply only when the instance property is at its default value") make it additive to template instantiation rather than a replacement ([Roblox Studio Beta post](https://devforum.roblox.com/t/studio-beta-introducing-ui-styling/3660722)). The weakest claim evidentially is claim 1: there is no quantitative data on Roblox reuse patterns, only thread content and library design.

## Roblox templates are prefabs, and no engine outside the web lineage chose selectors

The Roblox evidence for claim 1 is qualitative but consistent. Beginner and intermediate Scripting Support threads from 2024 show the canonical idiom: a hidden template instance that is `:Clone()`d per data item, with replies advising to "parent the `PlaceholderCategory` to the script and set its visibility to false" so the template survives as a reusable prototype ([DevForum](https://devforum.roblox.com/t/how-do-i-make-this-system-better/3025569)); inventory and shop threads use the same pattern inside a `UIGridLayout` ([DevForum](https://devforum.roblox.com/t/making-an-inventory-system/260253)). Every declarative framework then formalises the same unit as `function(props) -> instances`: Roact's function components "are just functions that accept props as their only argument, and return some elements" ([Roact docs](https://roblox.github.io/roact/guide/components/)); Roblox's own May 2024 React Luau guide teaches "reuseable components" via composition, notes that "The React styling property always matches the instance property name," and describes no theming system at all ([DevForum](https://devforum.roblox.com/t/how-to-react-roblox/2964543)); Vide's README `Counter` is a plain function returning `create "TextButton" { ... }` ([Vide](https://github.com/centau/vide)); Iris configures appearance through a global config table, not selectors ([Iris](https://github.com/SirMallard/Iris)). The community tooling even runs in the direction the thesis predicts: Vigets converts hand-built GUIs *into* Vide components, confirming that template and component are one mental unit ([DevForum](https://devforum.roblox.com/t/vigets-convert-your-roblox-guis-into-vide-components-free/4760321)). A structural reason this idiom is so natural, which the post should state explicitly, is that Roblox's appearance modifiers (UICorner, UIStroke, UIPadding, UIGradient) are *child instances*, so a template is already a composition of base object plus modifiers and `Clone()` copies the whole styled bundle ([Creator Hub](https://create.roblox.com/docs/en-us/ui/appearance-modifiers)).

Three community attempts at CSS-for-Roblox preceded the native feature, and all were niche: StyleScript (Dec 2020), whose author conceded "It would be hard to make a height and a width property" ([DevForum](https://devforum.roblox.com/t/stylescript-script-your-style/947931)); RSS 1.0.0 (Jan 2022), which drew the reply "This seems kinda useless since people who don't know CSS would have to learn it" and that Roact already handles this ([DevForum](https://devforum.roblox.com/t/rss-100-ui-styling-made-easier/1625385)); and RSML (May 2025), which appeared nine days after the native Studio beta ([DevForum](https://devforum.roblox.com/t/css-for-roblox-rsml/3671593)). The 2022 "Roact already handles this" reply is the closest thing in the record to a community articulation of the "wrong kind of reuse" argument, and it is one sentence from one person. Do not overstate it.

The convergent-evolution point is stronger than the Roblox-specific one. In October 2014 an Unreal developer asked why Slate style assets could not be shared across UMG screens; Epic's Nick Darnell answered that those assets "exist because they were developed before UMG," that "The long term plan is to make styling reusable, but not the way it was," that the replacement would be "style classes, that can be extended via blueprints or C++ and contain behaviors, allow bindings," and that the workaround was to "Wrap the styled element in a User Widget, such as a button, and reuse that" ([Unreal forums](https://forums.unrealengine.com/t/using-widget-style-assets-with-umg/296153)). That is an engine team stating that the right reusable unit carries behaviour, and Common UI's eventual answer (2021) was shared style *objects* referenced by widgets, not selectors ([Epic docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/common-ui-plugin-for-advanced-user-interfaces-in-unreal-engine)). Godot's docs say "most game components map directly to a scene" and that "Changing a property on an instance always overrides values from the corresponding packed scene" ([Godot](https://docs.godotengine.org/en/stable/getting_started/step_by_step/instancing.html)). Dear ImGui is one style struct with push/pop scoping and says reuse is "your own one-liner wrappers" ([ImGui FAQ](https://github.com/ocornut/imgui/blob/master/docs/FAQ.md)). Unity's own manual draws the prefab-to-component line for you: UXML attribute overrides are "similar to modified properties in the Unity Prefab system" ([Unity Manual 2021.1](https://docs.unity3d.com/ru/2021.1/Manual/UI-system-compare.html)). The one engine that adopted a selector cascade, Unity UI Toolkit, did so by explicitly importing the web ("based on, and inspired by, standard web technologies"), and its staff justified USS by familiarity and mergeable text files while calling the formats "implementation details" ([Unity discussion](https://discussions.unity.com/t/why-is-unity-creating-yet-another-ui-system/850204)); the official runtime recommendation stayed uGUI/prefabs ([Unity Manual](https://docs.unity3d.com/Manual/UI-system-compare.html)).

Where claim 1 needs qualifying: "left to their own devices" is true for *structure* reuse but misleading about *value* sharing. A September 2020 thread asking how to add a dark theme to "50 or more GUI instances" got only name-prefix hacks and `GetDescendants` recolour loops, and no answer about built-in support ([DevForum](https://devforum.roblox.com/t/dark-theme-in-game/756091)). The one semantic-token system Roblox had before 2025 was Studio's plugin-facing `StudioTheme:GetColor` with 130 enumerated roles, consumed imperatively in code ([Creator Hub](https://create.roblox.com/docs/reference/engine/enums/StudioStyleGuideColor)). So the accurate statement is: developers converged on templates for reuse *and* visibly lacked, and hacked around, a shared-value layer. That lack is what the native StyleSheets filled, which matters for the section on Roblox below. The researchers found no download counts, surveys or adoption statistics for any of this; the evidence is thread content and library design.

## The cascade was designed for three strangers, and its inventor called the result a failure

Claim 2 has the best primary sources of the five, but the post's framing needs a correction. Lie's 10 October 1994 proposal states two goals, "giving readers a richer visual (or auditory and tactile) environment while they retain control if necessary" and "providing authors and publishers with stylistic influence," and defines the cascade as "an ordered list (cascade) of style sheets" supplied by multiple parties where "the user/browser specifies initial preferences and hands the remaining influence over to the style sheets" ([Lie 1994](https://www.w3.org/People/howcome/p/cascade.html)). The original cascade was literally a negotiation of percentages (`h2.font.size = 20pt 40%`, combined as "a weighted average of the two requests"). The W3C's own history says "the style of a document couldn't be designed by either the author or the reader on their own," and that at WWW3 Darmstadt in April 1995 the opposing camp argued the author must be in charge while Bos and Lie argued "the user ... should be given the last word when conflicts arise" ([W3C history](https://www.w3.org/Style/CSS20/history.html)). Lie's 2005 thesis lists six web requirements, every one presupposing a document delivered to a stranger: the author "has no way of knowing in advance" the device, the reader may add preferences, "If a style sheet fails to appear, the content should still be presentable" ([Lie thesis](https://www.wiumlie.no/2006/phd/)). The thesis uses "application" only to mean desktop software and treats web apps nowhere; its single forward-looking mention is a research question, "Can cascading be used to determine GUI settings of an application?"

**The correction:** the founding unknowns are the *reader, device and delivery*, not the content. "Reuse" in the founding texts always means *content* reused under many presentations: "The benefit of a high abstraction level is that the content can be reused in many contexts" ([Lie thesis](https://www.wiumlie.no/2006/phd/)). The idea of reusing style *rules* across many pieces of markup is absent from the founding texts and only becomes the industry meaning with OOCSS in 2009. CSS Zen Garden, launched May 2003 with the rule "You may modify the style sheet in any way you wish, but not the HTML" ([csszengarden.com](https://csszengarden.com/)), is the purest demonstration of the *founding* direction: fixed, known content under unlimited style variation. It demonstrates nothing about the opposite direction (one style set, many contents), which is what application UI needs. The post's phrase "a document of unknown content that you want to look nice" describes the CMS/template use case, which is real but later; Lie's own version is a document of known content for an unknown reader. The post should say which it means, because the counterarguments split exactly along this line (see the steelman section).

The decoupling's illusory quality has been argued continuously for twenty years, and the critiques are quotable. In July 2006 on www-html, "Spartanicus" wrote that Zen Garden "falsely suggests" CSS can fundamentally change a site's layout and that "To create this illusion it litters the markup with spurious code which makes the code inflexible and difficult to maintain" ([www-html 2006](https://lists.w3.org/Archives/Public/www-html/2006Jul/0005.html)). In September 2026 a Hacker News commenter made the same point about Jo Sprague's Firefox.com rebuild: the Zen Garden model worked because "everyone was using a single markup file," and separating markup from styling "means that the CSS rules need a way to be mapped onto the DOM," with that mapping implicit ([HN](https://news.ycombinator.com/item?id=49713262)); Sprague herself concedes Firefox.com "has only one design" ([Sprague 2026](https://josprague.com/blog/the-css-zen-garden-dream-finally-shipped/)). Lie's thesis contains the sharpest version from inside the tent: "The class problem is a specific case of the generic markup problem," meaning author-chosen class attributes make style sheets that *nobody else can cascade with*, and "It is impossible to write one user style sheet that cascades well with all author style sheets on the web" ([Lie thesis](https://www.wiumlie.no/2006/phd/)). So the semantic-class model does not even deliver the original promise.

The practitioner lineage is a clean chain of people disabling more of the cascade at each step, and it is worth presenting as such: Yandex's 2006 experience that "edits to one page could break others" led to "independent blocks" that use only class names (ClientSide 2007) and then BEM ([Smashing Magazine](https://www.smashingmagazine.com/2013/02/the-history-of-the-bem-methodology/)); Nicole Sullivan's OOCSS (2009) said "An object should look the same no matter where you put it" ([OOCSS wiki](https://github.com/stubbornella/oocss/wiki)); SMACSS (2011) named "depth of applicability" and warned that deep selectors enforce "a much greater dependency on a particular HTML structure" ([SMACSS](https://smacss.com/book/applicability)); Nicolas Gallagher (2012) argued "The primary purpose of a class name is to be a hook for CSS and JavaScript" and "The most reusable components are those with class names that are independent of the content" ([Gallagher](https://nicolasgallagher.com/about-html-semantics-front-end-architecture/)); Harry Roberts (2014) called specificity "a trait best avoided" ([Roberts](https://csswizardry.com/2014/10/the-specificity-graph/)); Christopher Chedeau's November 2014 deck listed seven problems and observed "CSS was designed with a single file in mind" ([Chedeau](https://speakerdeck.com/vjeux/react-css-in-js)); and Adam Wathan (2017) reframed the whole debate as dependency direction, with the line the post should quote: "In this model, your HTML is restyleable, but your CSS is not reusable," followed by the question "For the project you're working on, what would be more valuable: restyleable HTML, or reusable CSS?" ([Wathan](https://adamwathan.me/css-utility-classes-and-separation-of-concerns/)). Wathan names Zen Garden as "The quintessential example of this approach," so the post's Zen Garden framing has direct precedent. Pete Hunt's 2013 "Templates separate technologies, not concerns" is the hinge that relocated the concern boundary from the language to the component ([Strumpflohner notes](https://juri.dev/blog/2013/12/react-rethingking-best-practices)), though the researchers note the slide wording is from search snippets and should be checked against the JSConf EU video before being quoted verbatim.

The most useful single contrast for the post, which the researchers drew from the sources rather than quoting from one: Lie's requirement that the author "has no way of knowing in advance" the rendering context, versus Chedeau's component maintainer whose problem is that *other people in the same codebase* can "modify the style of the internals via selectors" and so "feel fearful of changing code." The cascade was built for mutual ignorance; application UI is a regime of mutual knowledge. Keith J. Grant's 2015 rebuttal to Chedeau is the strongest statement of the opposing dependency direction and deserves a fair quote: CSS should be "a modular, reusable API" that markup depends on, portable across "Every JavaScript library and every HTML templating language" ([Grant 2015](https://keithjgrant.com/posts/2015/05/against-css-in-js/)).

## Every scoping tool re-opened one hole, and it is shaped like a token

Claims 3 and 4 are best argued together, because the evidence for them is the same: when you look at what each encapsulation system *lets through*, the list is short and identical everywhere. The chronology is dense. CSS Modules (2015) defined a module as "a CSS file where all class names and animation names are scoped locally by default" ([CSS Modules](https://github.com/css-modules/css-modules)), and Glen Maddern called Chedeau's talk "a watershed moment" ([Maddern](https://glenmaddern.com/articles/css-modules)). Rich Harris's 2017 Svelte post said "Everything in CSS is global," described the "append-only stylesheet" where "there's no way of knowing which code can safely be removed," and promised "No more leakage, no more unpredictable cascade" ([Svelte blog](https://svelte.dev/blog/the-zen-of-just-writing-css)). Vue's `<style scoped>` applies "to elements of the current component only" ([Vue](https://vuejs.org/api/sfc-css-features.html)); Angular's emulated encapsulation "ensures that a component's styles do not leak out" ([Angular](https://angular.dev/guide/components/styling)). Max Stoiber (2019): "If I delete a component, I delete its CSS too" ([Stoiber](https://mxstbr.com/thoughts/css-in-js)). The second wave treated scoping as settled and attacked runtime cost and ordering: StyleX (Meta, 2023) "guarantees no specificity conflicts in the generated CSS" and is "aligned with the principles of encapsulation introduced by React Native's styling system" ([StyleX](https://stylexjs.com/blog/introducing-stylex/)); Meta's 2025 engineering post describes `stylex.props` as "a deterministic merge of style objects" where "The last style always wins!", says "Global and complex selectors are disallowed to avoid styling at a distance," and reports atomic classes "reduced CSS size by 80%" ([Meta](https://engineering.fb.com/2025/11/11/web/stylex-a-styling-library-for-css-at-scale/)). The CSS spec itself now concedes the point: the css-cascade-6 editor's draft says "Many existing tools implement 'scoped styles' by applying a unique class or attribute to every element," and Miriam Suzanne's explainer describes @scope as "a native CSS approach for what many authors are already doing" with CSS Modules, Vue and Styled-JSX ([css-cascade-6](https://drafts.csswg.org/css-cascade-6/), [Scope explainer](https://css.oddbird.net/scope/explainer/)). The same subtree-scoping instinct shows up in a non-styling spec: a named scroll timeline "can only be set as the controlling timeline of a direct descendant element" by default and must be explicitly lifted with `timeline-scope` ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/timeline-scope)). Una Kravets's container-query rationale is the explicit component framing: components "still don't own their styles, and that doesn't work when our design systems are component-based and not page-based" ([web.dev](https://web.dev/articles/new-responsive)).

The migration write-ups are where "only tokens cascade" stops being advocacy and becomes observed practice. GitHub has run on **100% CSS Modules since June 2026**, removed `styled-components` from dotcom, got "55% less time to server-side render a page," and states what stayed global: "Our theming variables have always been defined in CSS through our `@primer/css` package" ([GitHub](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)). Linear finished a styled-components-to-StyleX migration in August 2026 (>1,000 PRs) partly because `styled(Button)` "made it too easy to restyle a component from the outside" ([InfoQ](https://www.infoq.com/news/2026/09/linear-stylex-meta/)). Atlassian standardised on build-time Compiled with tokens delivered via `@atlaskit/tokens` ([Atlassian RFC-73](https://community.developer.atlassian.com/t/rfc-73-migrating-our-components-to-compiled-css-in-js/85953)). Tailwind "uses CSS variables" for theme values ([Tailwind](https://tailwindcss.com/docs/styling-with-utility-classes)); Panda compiles tokens to `var(--colors-white)` ([Panda](https://panda-css.com/docs/overview/why-panda)); Linaria applies dynamic styles "using CSS custom properties" ([Linaria](https://github.com/callstack/linaria)); Polaris delivers tokens as `--p-*` custom properties and its web components, behind Shadow DOM, tell apps they cannot reach `.Polaris-*` internals ([Polaris](https://raw.githubusercontent.com/Shopify/polaris/main/polaris-tokens/README.md), [shopify.dev](https://shopify.dev/docs/apps/build/app-home/polaris2)). Survey data confirm the centre of gravity: in State of CSS 2025, **"None" was the most-selected CSS-in-JS answer at 56.7% of 3,718 respondents** and Tailwind led frameworks at 51.3% ([State of CSS 2025](https://2025.stateofcss.com/en-US/other-tools/)).

Claim 4's definition of what deserves sharing has an unusually formal backing. The W3C Design Tokens Community Group shipped its first stable format, version 2025.10, on 28 October 2025, with over twenty editors from Adobe, Google, Microsoft, Meta, Salesforce, Shopify and Figma ([W3C DTCG](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)); it is explicitly "not a W3C Standard nor is it on the W3C Standards Track" ([DTCG 2025.10](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/)). Its value types are color, dimension, fontFamily, fontWeight, duration, cubicBezier and number, with composites for border, transition, shadow, gradient and typography, and it contains no concept of selectors, specificity or cascade. Across Material 3, Primer, Atlassian, Spectrum, Carbon and Polaris the tokenised categories converge on colour, typography, space, radius/shape, elevation, opacity and motion; none tokenises layout structure or component anatomy ([Atlassian](https://atlassian.design/foundations/tokens/design-tokens/), [Spectrum](https://spectrum.adobe.com/page/design-tokens), [Carbon](https://carbondesignsystem.com/elements/themes/overview/)). That bounded list matches the post's list almost exactly. The component tier of tokens is repeatedly described as optional and limited: Primer says component tokens "are limited and functional tokens are preferred" ([Primer](https://primer.style/foundations/color/overview)); Nathan Curtis's 2024 talk abstract says "Many design systems can live forever without nary a component-level design token" ([SmashingConf](https://smashingconf.com/antwerp-2024/speakers/nathan-curtis)).

The native toolkits show what "a component owns its relationship to tokens" looks like concretely. Jetpack Compose's API guidelines say to "Prefer explicit inputs and configuration options in your components, such as function parameters," that theme `CompositionLocal`s "should be read in default expressions, not inside the component body," and that defaults should live in a public `ComponentDefaults` object ([androidx guidelines](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/docs/compose-component-api-guidelines.md)). Android's official XML-to-Compose migration guide says "Styles have no **direct** equivalent in Compose" and, for `style="@style/MyPrimaryButton"`, "don't try to replicate the style inline. Instead, suggest creating a specific composable" `MyPrimaryButton(onClick = ...)` ([Android](https://developer.android.com/develop/ui/compose/designsystems/views-to-compose)). That is a platform vendor telling developers to replace a style rule with a component. Flutter's `Theme.of` is "essentially just a single HashMap access" and "Material components typically depend exclusively on the colorScheme and textTheme" ([Flutter](https://api.flutter.dev/flutter/material/ThemeData-class.html)). The three desktop toolkits that imported CSS wholesale all retreated: Qt's docs now say "Style sheets are a tool for prototyping and for small, local adjustments," that Qt widgets by default do "not automatically inherit" font and colour from the parent, and "Don't use this function to switch themes at runtime" ([Qt](https://doc.qt.io/qt-6/stylesheet.html), [Qt syntax](https://doc.qt.io/qt-6/stylesheet-syntax.html)); JavaFX's own mailing list documents the origin pathology where "simply specifying -fx-base in your own AUTHOR stylesheet elevates hundreds of styles from Modena to AUTHOR level" ([openjfx-dev](https://mail.openjdk.org/pipermail/openjfx-dev/2024-July/047827.html)); GNOME's Brage Fuglseth says theming "depends on a misuse of GTK's styling system" and "is an unsupported hack," Jason Francis says "using libadwaita means the libadwaita styles are a critical API dependency of the app," and the sanctioned surface is a list of CSS variables (`--accent-bg-color`, `--window-bg-color`) ([GNOME Discourse](https://discourse.gnome.org/t/why-and-how-libadwaita-prevents-theming/17079), [libadwaita](https://gnome.pages.gitlab.gnome.org/libadwaita/doc/main/css-variables.html)). The theming case studies fit the same shape: Atlassian converted Jira's hard-coded hex values to roughly **300 tokens with 90% of the work automated**, after which dark and higher-contrast themes were buildable "quickly," while the long tail was 1,200+ images across 60+ teams that tokens cannot carry ([Atlassian](https://www.atlassian.com/blog/announcements/the-story-of-dark-theme)); GitHub produces nine colour modes by swapping palettes under a fixed functional-token API ([primer/primitives](https://github.com/primer/primitives)); Material You components "built to respond to dynamic color" need no change when the system swaps role values ([material.io](https://material.io/blog/start-building-with-material-you)).

Two qualifications to claims 3 and 4 are mandatory. First, "nothing is worth cascading" is false as stated; the defensible claim is "nothing *selector-driven* is worth cascading." Shadow DOM: "Inheritable styles ... continue to inherit in shadow DOM" and component authors "provide hooks (in the form of CSS custom properties)" ([web.dev](https://web.dev/articles/shadowdom-v1)). React Native: "React Native still has the concept of style inheritance, but limited to text subtrees," with the stated rationale that "Text properties that could inherit from outside of the props would break this isolation," and the recommended replacement for cascading typography is to "create a component `MyAppText`" ([React Native](https://reactnative.dev/docs/text)). StyleX: inheritance "is the _only_ form of style-at-a-distance that StyleX allows" ([StyleX](https://stylexjs.com/docs/learn/thinking-in-stylex/)). Angular: "Custom properties inherit down the DOM tree" even under emulated encapsulation ([Angular](https://angular.dev/guide/components/styling)). Svelte wins *through* the cascade, with a 0-1-0 specificity bump and `:where()` ([Svelte docs](https://svelte.dev/docs/svelte/scoped-styles)). `currentColor` is the textbook case of a component deliberately wanting an inherited value ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value#currentcolor_keyword)). Second, "completely and deterministically" overstates the native toolkits. Theme *values* in SwiftUI, Compose, Flutter and Godot still arrive by nearest-ancestor lookup, and Compose's own docs warn that "`CompositionLocal` makes a composable's behavior harder to reason about" because of "implicit dependencies" and "no clear source of truth," recommending "pass composables only what they need" ([Compose docs](https://developer.android.com/develop/ui/compose/compositionlocal)). The accurate formulation, which the researchers reached independently in two notes, is: **rules do not cascade; values do.** Godot's docs even call theme propagation "cascading," so the post should define the word before using it ([Godot](https://docs.godotengine.org/en/stable/tutorials/ui/gui_skinning.html)). One more wrinkle: Compose shipped an experimental Styles API in 2026 that is "similar to CSS styles," though it keeps last-write-wins property objects and typed `StyleState` rather than selectors, and its stated motivation is performance and reducing parameter sprawl ([Android](https://developer.android.com/develop/ui/compose/styles)). The vocabulary is drifting back toward "style" even where the mechanism is not.

| What crosses the component boundary | Shadow DOM | React Native / RNW | StyleX | Svelte / Vue / Angular | Compose / Flutter / SwiftUI | Godot |
|---|---|---|---|---|---|---|
| Selector reach from outside | No (`::part` only) | No | No (complex selectors disallowed) | No (hashed class / attribute) | None exists | None exists |
| Inherited text properties (font, colour, direction) | Yes | Only inside `<Text>` subtrees | Yes, "only" style-at-a-distance | Yes | Via theme object, read by component | Via theme chain |
| Custom properties / theme values | Yes, the sanctioned hook | Via composition (`MyAppText`) | `defineVars` | Yes | `EnvironmentValues` / `CompositionLocal` / `InheritedWidget` | Theme resource, nearest ancestor |
| Source-order resolution | Yes | Replaced by deterministic precedence | Replaced by deterministic merge | Yes (Svelte bumps specificity) | Last parameter wins | Local override wins |

## Server-driven UI sends nouns and variants, never pixels

Claim 5 is well supported structurally and unsupported by any direct quote of the kind the post wants. Where companies publish their schema, the server-side vocabulary is document-like, Page or Screen to Section to Component or Entity, with enumerated variants. Airbnb's Ghost Platform wraps each Section in a container carrying a `sectionComponentType` enum (`HERO`, `TITLE`), and InfoQ notes "the only styling reference is the `TextStyle` type used by `TitleSection`" ([InfoQ on Airbnb](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)). Spotify's Hub Framework JSON has `component.id`, `text.title`, `images.main`, `target` and `children`, and "The page does not mention style or raw styling properties" ([Hub JSON guide](https://spotify.github.io/HubFramework/json-programming-guide.html)). Yelp's CHAOS sends `"style": "primary"` and `"textStyle": "heading1-bold"` ([Yelp 2025](https://engineeringblog.yelp.com/2025/07/chaos-inside-yelps-sdui-framework.html)), and Yelp's Konbini is the most mechanical version of "the design system is the vocabulary": it is "an auto-generated bridge library" that exposes "the Cookbook component interfaces to Python code," regenerated from JSON component-interface definitions, so the server can only say what Cookbook can render; "Style and size are enumerated values (e.g., 'primary,' 'small'). Colors are referenced as named tokens" ([Yelp 2026](https://engineeringblog.yelp.com/2026/04/keeping-server-driven-ui-consistent-across-platforms.html)). Shopify's Shop app splits it as "Server controls: which sections appear, the layout type, display size ... Client controls: how components render" ([Shopify](https://shopify.engineering/server-driven-ui-in-shop-app)). Netflix "did not want to reinvent HTML for UMA, so they built CLCS as a wrapper around Hawkins," its design system ([InfoQ on Netflix](https://www.infoq.com/news/2024/07/netflix-server-driven-ui/)). Apollo's SDUI guidance states the rule directly: "the client's goal is to handle pixels, not data," and "Rather than returning hex codes in a request for something like badge color, it's best to use a design system that operates on tokens" ([Apollo](https://www.apollographql.com/docs/graphos/schema-design/guides/sdui/client-design)).

Netflix's GraphQLConf 2026 deck is the single most quotable source for claim 5 and should anchor the section. Its spectrum runs from "Client-Driven: Client owns schema" through **"Coarse-Grained: Server decides WHAT, Client decides HOW"** to "Fine-Grained: Server controls props" and "Thin Client: Server owns render," and it illustrates "The Same Movie. Four Different APIs." with coarse-grained sending `"treatment": "BillboardEntityTreatment"` ("Server sends a signal") while fine-grained sends `"titleSize": 48, "padding": "24px 32px"` and thin-client is literally `<HTML>` ([Netflix](https://hosted-files.sched.co/graphqlconf2026/cb/Screens%20on%20Shuffle.pdf)). Two things in that deck sharpen the post. One, Netflix puts HTML at the *server-owns-render* extreme, which supports arguing that SDUI is HTML's semantic half without its stylesheet half. Two, Netflix's stated lesson is the SDUI analogue of class-name explosion: "Schema should tie into design. Every minor visual variation became a new treatment. Near-duplicates compounded. Schema and design drifted apart." The fix is to make the vocabulary *be* the design system's vocabulary, which is what Yelp did mechanically. Microsoft's Adaptive Cards is the clearest formalisation for third-party authors: "Semantic instead of pixel-perfect," "Card Authors own the content, Host App owns the look and feel," and an explicit document analogy, "an intermediate layer which is 'expressive enough' in the same way Markdown is expressive enough for documents" ([Adaptive Cards](https://learn.microsoft.com/en-us/adaptive-cards/)). Slack's button `style` is only `primary` and `danger`, and Discord's six button styles come with no colours specified ([Slack](https://docs.slack.dev/reference/block-kit/block-elements/button-element/), [Discord](https://docs.discord.com/developers/components/reference)); these prove the semantic-palette approach scales to untrusted authors.

Now the gaps. No company source found makes the explicit claim "we redesigned our design system without touching server content." The researchers tried every route to Airbnb's, Lyft's and Faire's Medium posts and got 403s; those are cited through InfoQ and snippets. The restyle-without-server-change property follows *by construction* from token-and-variant payloads, and the post can argue it from the published schemas, but it should be presented as an inference, not a quote. No SDUI source mentions CSS Zen Garden or "semantic markup"; that analogy is the author's own and should be flagged as such. The analogy is also not quite the same direction as Zen Garden: Zen Garden fixes the markup and varies the style, whereas SDUI varies the arrangement over a fixed component set whose style the client owns. The useful shared property is that both make the style author and the content author different parties with a stable contract between them; the contract in Zen Garden is HTML elements plus pre-planted hooks, and in SDUI it is a component registry. Versioning is the other honest caveat: Netflix's "Capabilities. Client declares what it can render. Server returns only that. No versioning. No negotiation" and Yelp's per-app-version gating mean adding vocabulary is safe, but renaming or removing a component is a coordinated change, closer to deprecating an HTML element than to swapping a stylesheet. Finally, Thoughtworks has kept SDUI at Trial since 2022 and warns it "needs a strong business case and disciplined engineering to avoid a 'god-protocol'," recommending it "only for highly dynamic parts of an app, not as a replacement for all UI development" ([Thoughtworks](https://www.thoughtworks.com/radar/techniques/server-driven-ui)); Nubank's trajectory from templates that "almost fit" to "we're building a scripting language" is the cautionary case for pushing *behaviour* server-side ([InfoQ Nubank](https://www.infoq.com/presentations/mobile-server-driven-ui-scale/)). The post should present SDUI as the stable equilibrium for the content-arrangement problem, not as a general architecture.

## The cascade's defenders are right about the user tier, and Shadow DOM proves it

The strongest counterargument is not "global is tidier than local." Nobody serious argues that; PPK, the most explicit defender of "cascade-induced global scope," concedes in the same post that a component whose button must follow the component's style needs local scope, and endorses the hybrid of "default block level margins, your typography, etc high up" with components scoping the rest as "the correct solution" ([PPK](https://www.quirksmode.org/blog/archives/2018/04/css_global_scop.html)). The post's real opponent is the claim that the cascade exists to let parties who never meet co-author a presentation. Jeremy Keith's "Influence" recounts Lie's 1994 percentage negotiation and concludes that with user style sheets dead, "Web design today is dictatorial," every CSS line being "a suggestion to a web browser—not a demand" ([Keith](https://dev.to/adactio/influence-2cda)). Miriam Suzanne's 2024 talk abstract frames the cascade's job as "styling unknown content, with unknown collaborators, on an infinite and unknowable canvas" ([beyond tellerrand](https://beyondtellerrand.com/blog/btconf-berlin-2024-video-miriam-suzanne)); her layers explainer says "Cascade Origins help to balance styling concerns across stakeholders" ([Layers explainer](https://css.oddbird.net/layers/explainer/)). Every Layout makes the inheritance-reduces-repetition case concretely: found designs on axioms like "measure never exceeds 60ch," apply them globally, enumerate only exceptions, and "do most of our styling with the least of our code," with element selectors "the hallmark of a comprehensive design system" ([Every Layout](https://every-layout.dev/rudiments/axioms/), [global and local](https://every-layout.dev/rudiments/global-and-local-styling/)).

The cases that most embarrass sealed-component styling are the **unknown style author** ones, and the post must distinguish them from unknown content. The cascade's user tier is a standardised accessibility mechanism: user `!important` beats author `!important` ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_cascade/Cascade)); WCAG 2.1 SC 1.4.12 presumes author CSS is overridable from outside and fails content only if it is "actively and purposely preventing the properties from being added" ([W3C](https://www.w3.org/WAI/WCAG21/Understanding/text-spacing.html)); forced-colors mode has the browser rewrite colours at paint time ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors)), and with Shadow DOM every component must carry its own forced-colors handling, as Microsoft's Fluent UI does ([Fluent UI](https://learn.microsoft.com/pt-br/fluent-ui/web-components/design-system/high-contrast)); reader modes strip author CSS entirely ([Soueidan](https://sarasoueidan.com/blog/tips-for-reader-modes/)); Stylus and Obsidian's theme ecosystem exist because page styles are reachable, though Obsidian is a hybrid, exposing "more than 400 different CSS variables" while still permitting arbitrary selectors ([Obsidian](https://docs.obsidian.md/Themes/App+themes/Build+a+theme)). Jim Nielsen's point is the cleanest: global CSS is an "unofficial [styling API] without any kind of semver contract," and Shadow DOM means "people can't peer into your component and write selectors that target the things they want to style" ([Nielsen](https://blog.jim-nielsen.com/2021/shadow-dom-and-the-styling-api/)). For *unknown content* (CMS output, markdown, embeds) the pro-cascade case is weaker, because a prose wrapper component with element selectors inside it handles it, and Suzanne's own spec treats that as a scope problem rather than an isolation problem. The honest framing available to the post: the cascade's user tier is valuable on the web and absent on Roblox, so the thesis holds for platforms with no user party and must be stated that way rather than as "user overrides don't matter." VS Code is the useful counter-counterexample, a mature user-themable UI whose themes are JSON colour slots with no CSS ([VS Code](https://code.visualstudio.com/api/extension-guides/color-theme)), but note that VS Code themes cannot touch layout, spacing or typography; token-only theming is a strict subset of what userstyles allow.

Shadow DOM is the most persuasive evidence on the cascade's side because it is a shipped experiment, not an opinion. The platform's hard encapsulation (2016–2018) has been followed by a decade of attempts to punch cascade-shaped holes back in: `::part()` (which "doesn't work deeply"), the open-stylable shadow roots issue opened by Justin Fagnani in December 2020 and still open with 250+ comments because "strong style encapsulation is a major hinderance" ([WICG #909](https://github.com/WICG/webcomponents/issues/909)), the 2024 `adoptStyles` proposal that bridges shadow trees to page styles *via cascade layers* ([csswg-drafts #10176](https://github.com/w3c/csswg-drafts/issues/10176)), and a `::theme()` that remains unspecified. Fagnani in September 2024: "Many people need to be able to arbitrarily style allowed elements deep down the shadow tree. That isn't solved by anything today" ([W3C list](https://lists.w3.org/Archives/Public/public-webapps-github/2024Sep/0058.html)); the researchers caution that the sentence carries quote markers in the email and may be him quoting another participant. Nolan Lawson calls it "a *coordination problem*, not a technical problem," asks "Will every web component on npm need to enable open-stylable shadow roots?", and supplies the steelman *for* encapsulation too: restyle a third-party dropdown via global CSS, and six months later a security update renames a class and "Everything's broken" ([Lawson](https://nolanlawson.com/2023/12/30/shadow-dom-and-the-problem-of-encapsulation/)). Manuel Matuzo after a year with web components: global focus styles do not reach shadow DOM so he repeats them in every interactive component, and "If web components couldn't consume custom properties from the outside, I would've thrown them out of the window months ago" ([Matuzo](https://matuzo.at/blog/2023/pros-and-cons-of-shadow-dom)). The expected objection to the post is "your copy-and-configure templates are Shadow DOM without `::part`," and the post should answer it before a reader raises it. The answer the evidence supports: hard encapsulation was wrong, *and* every escape hatch that actually shipped (custom properties, `::part`) is a named, author-declared contract rather than arbitrary selector reach, which is closer to tokens than to style sheets. Fagnani himself separates theming ("quite a different problem") from migration.

The spec authors' deliberate choice is the other thing to engage with directly. Suzanne's scope explainer says "Shadow-DOM is not designed for the common 'design system' approach," that full isolation "feels like a significantly different approach" the proposal does not attempt, and that "We have intentionally gone in the other direction, making scope proximity less powerful than specificity in the cascade" so global styles can "flow through, interact with, and even override scoped styles" ([Scope explainer](https://css.oddbird.net/scope/explainer/)). Bramus: "@scope limits the reach of the selectors. It doesn't offer style isolation" ([Chrome](https://developer.chrome.com/docs/css-ui/at-scope)). Kravets: "Cascade layers do not solve scoping" ([Chrome](https://developer.chrome.com/blog/cascade-layers)). Suzanne also warns against the instinct to "create a layer for each component" and offers the formula "Scopes describe what we are styling, while layers describe why" ([CSS-Tricks](https://css-tricks.com/css-cascade-layers/)). The CSS custodians looked at component encapsulation and built weak scoping on purpose. The post's claim 3 cites @scope as evidence for scoping; the counter-reading is that @scope is evidence the platform *rejected* the sealed-component model for design systems. Both readings are defensible; the post should acknowledge the second.

The academic literature is not a steelman for the cascade, but it is not clean evidence for components either. Mazinanian, Tsantalis and Mesbah (FSE 2014) found across 38 systems and 91 CSS files that "The median value for the percentage of duplicated declarations is 68%" versus 5–20% in procedural code, and their motivation names "inheritance, cascading and specificity" as what makes CSS hard to maintain ([FSE 2014](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf)); Mesbah and Mirshokraie (ICSE 2012) found "an average of 60% unused CSS selectors" across fifteen deployed applications ([ICSE 2012](https://people.ece.ubc.ca/amesbah/resources/papers/icse12.pdf)). The defender's reply is that these measure undisciplined CSS, and no study tests a `:root`-axioms plus `@layer` codebase; equally, no study shows component-scoped styling reduces duplication, and per-component files would produce *more* type-I duplication unless tokens are shared. The design-system drift literature is agnostic between "global style layer" and "token layer"; it argues against ungoverned copying, which is exactly the Roblox template's failure mode when a clone has no upstream link ([Frost](https://bradfrost.com/blog/post/design-system-components-recipes-and-snowflakes/), [Every Layout](https://every-layout.dev/rudiments/axioms/)). Runtime CSS-in-JS has measured cost (Sam Magura's 54.3 ms versus 27.7 ms per render on one app, with a partially retracted concurrent-rendering claim) ([Magura](https://dev.to/srmagura/why-were-breaking-up-wiht-css-in-js-4g9b)), but that argues for build-time tooling, not for the cascade.

## Roblox StyleSheets praise tokens and queries, not reuse

The post cannot avoid this, and the record is more favourable than it looks. The timeline: Studio beta 22 May 2025 ([DevForum](https://devforum.roblox.com/t/studio-beta-introducing-ui-styling/3660722)), Client beta publishable to live experiences 26 August 2025 ([DevForum](https://devforum.roblox.com/t/client-beta-you-can-now-publish-styles-in-your-experience/3901480)), full release 20 January 2026 ([DevForum](https://devforum.roblox.com/t/full-release-ui-styling-is-officially-released/4275082)), StyleQuery full release 11 May 2026 ([DevForum](https://devforum.roblox.com/t/full-release-stylequery-more-styling-features/4566519)), and Styling Transitions full release 27 July 2026 ([DevForum](https://devforum.roblox.com/t/full-release-styling-transitions/4646870)). The design is "inspired by CSS": CollectionService tags as classes, `#Name`, `:Hover`/`:Press` states, `::UICorner` pseudo-instances, `>` and `>>` combinators, `$Token` attributes "comparable to CSS variables," `@Query` built-ins such as `@ReducedMotionEnabledTrue` and `@PreferredInputTouch`, and Roblox publishes its own CSS mapping table ([Creator Hub](https://create.roblox.com/docs/en-us/ui/styling.md), [StyleRule](https://create.roblox.com/docs/en-us/reference/engine/classes/StyleRule.md), [CSS comparisons](https://create.roblox.com/docs/en-us/ui/styling/css-comparisons)). Roblox's stated motivation includes the exact separation claim the post attacks: "Styling separates defining the structure of UI elements from their visual appearance" ([DevForum](https://devforum.roblox.com/t/client-beta-you-can-now-publish-styles-in-your-experience/3901480)).

Three features of the record let the post address it head-on rather than wave it away. First, **the praise clusters on tokens and on things the engine could not do declaratively at all.** Studio-beta replies: "will be really useful for light/dark toggles and user color preferences," compared to Figma's variable system; praise for no longer maintaining "7 frames for each theme" ([DevForum](https://devforum.roblox.com/t/studio-beta-introducing-ui-styling/3660722)). Transitions-thread replies say they can drop their animation modules; StyleQuery replies celebrate not writing positioning code for every screen ([DevForum](https://devforum.roblox.com/t/full-release-styling-transitions/4646870), [DevForum](https://devforum.roblox.com/t/full-release-stylequery-more-styling-features/4566519)). Nobody in these threads describes replacing a component or template architecture with style rules; one React Luau user reports styling reduced their component code. Hover states, responsive queries and transitions are per-component concerns that a component could own if the engine exposed them to components; they arrived in a sheet because the sheet was the vehicle Roblox chose, not because a sheet is where they belong. Second, **the system's own constraints make it additive to templates.** "Overrides apply only when the instance property is at its default value," per-instance edits appear bold and beat the sheet, "Only one StyleSheet can apply to a given tree," and tokens and themes are attributes on StyleSheet instances ([DevForum](https://devforum.roblox.com/t/studio-beta-introducing-ui-styling/3660722), [Creator Hub](https://create.roblox.com/docs/en-us/ui/styling.md)). A cloned template with colours baked in largely ignores a sheet; adoption means starting from unstyled instances. Third, **the sharpest criticism is the tagging burden**, the thing that distinguishes a sheet from a component: "I felt like the whole idea of pseudoinstances would get confusing" and not knowing "how to feel about having to make 2 gazillion tags" ([DevForum](https://devforum.roblox.com/t/studio-beta-introducing-ui-styling/3660722)), plus "I've found using the StyleEditor to just be overall very unintuitive" and "Roblox should focus on core features" ([DevForum](https://devforum.roblox.com/t/full-release-ui-styling-is-officially-released/4275082), [DevForum](https://devforum.roblox.com/t/full-release-stylequery-more-styling-features/4566519)). Tags-as-classes push the mapping problem (which instances does this rule reach?) onto every instance, which is the SMACSS "depth of applicability" and HN "implicit mapping" critique reappearing on a new platform.

The honest concession the post should make: for a no-code user in the Studio editor, with no engine-level component primitive, a sheet with a visual editor is currently the *only* way to get hover states, light/dark themes, responsive queries and transitions declaratively. That is a real gain and connects directly to the author's 2022 argument that designers are excluded by code-only frameworks. The thesis survives if it is stated as "Roblox shipped the right *values* (tokens, states, queries, transitions) in the wrong *container* (selector rules over tags), because it lacks the container that every other engine has (a prefab, scene, user widget or component)." Roblox's own 2024 manifesto line from "Please, no more UI frameworks," that "We are long overdue proper tools for componentisation," is the author's prior statement of the missing container. The parallel to Unity UI Toolkit is exact and worth drawing: an engine imports the web's model for familiarity and tooling, its staff call the format "implementation details," and the community debate centres on complexity ([Unity discussion](https://discussions.unity.com/t/why-is-unity-creating-yet-another-ui-system/850204), [Unity Discussions 2024](https://discussions.unity.com/t/ui-toolkit-why-is-this-even-a-thing/1551019)). Two things the researchers could not find: any pre-2025 public announcement of StyleSheets (a 2024 "announcement" could not be substantiated, so do not claim one) and any comment from Roact, React Luau or Vide maintainers on the feature threads. The author should also disclose the obvious: as Fusion's author, a post arguing against style sheets argues for the model their library uses; the researchers deliberately excluded Fusion as evidence for that reason.

## A structure for the post, and where it meets the earlier ones

The argument reads most honestly if it opens with the concession and the Roblox counterexample rather than saving them. A workable arc: begin with the StyleSheets release and the "7 frames for each theme" praise, agree that the pain is real, then ask what the praised features have in common (tokens, states, queries, transitions) and observe that none of them is a selector. Move back to Lie's three strangers and Zen Garden, using the Wathan "restyleable HTML or reusable CSS" question as the pivot, and state the correction explicitly: the founding unknown was the reader, not the content, and the post is about the case where author and reader are the same team. Then the convergence section, led by the Unreal 2014 quote and the Android "create a specific composable" instruction, with the Meta/GitHub/Linear migrations as the "what stayed global" evidence and the boundary table above as the "rules don't cascade, values do" statement. Then the steelman in full: the user tier, forced-colors, Shadow DOM's escape hatches and Suzanne's deliberate weak scoping, resolved by noting that every shipped hatch is a declared contract and that Roblox has no user party. Then SDUI with the Netflix spectrum slide, Yelp's Konbini and Adaptive Cards' "Card Authors own the content, Host App owns the look and feel," with the inference-not-quote caveat. Close by returning to Roblox: right values, wrong container, and what the missing container is.

The connections to prior posts are concrete. "UI frameworks don't serve designers" (2022) argued that "Designers shouldn't have to learn code" and that code-first frameworks exclude them; the StyleSheets no-code Style Editor is Roblox's answer to that complaint, and the new post should say so, since the thesis is otherwise vulnerable to "you argued for designer-friendly tools and now reject the one Roblox shipped." The reconciliation is that tokens are the designer-facing surface (the Figma-variables comparison in the beta thread was made by the community unprompted), and that Yelp's tokens "maintained in a separate repository by designers and provided as JSON" show the designer-owned artefact can be a token file rather than a sheet ([Yelp 2026](https://engineeringblog.yelp.com/2026/04/keeping-server-driven-ui-consistent-across-platforms.html)). "UI layout hypotheses" (2023) claimed "Placement of UI elements can be informed by layouts, but cannot be prescribed by them"; the style-sheet argument is the same shape one layer over, style informed by tokens but not prescribed by rules, and the post can cite that parallel in a sentence. "Please, no more UI frameworks" (2024) argued that "packages with attributes are isomorphic to modern-day UI components" and that Roblox is "long overdue proper tools for componentisation"; a package exposing a "paint colour" attribute is a component owning its relationship to one token, which is claim 4 in the author's own earlier vocabulary, and StyleSheets putting tokens *as attributes on a StyleSheet instance* is Roblox half-agreeing. The 2026 Perfection draft is the natural landing: Chapter 4's "Widely shared parameters" section currently ends at its heading, immediately after "Better parameters for components" complains about positional arguments to `render_pause_menu` and `render_button`. Tokens are the canonical widely shared parameter, and the two models the research surfaced for passing them are Compose's `CompositionLocal` read in default parameter expressions (implicit, tree-scoped, with Compose's own warning that it makes behaviour "harder to reason about") and React Native's compositional `MyAppText` (explicit, no context at all). An immediate-mode library where "everything is data, everything is computation, everything is composition" has to choose between those, and the choice is exactly the "rules don't cascade, values do" line: a `UiContext` carrying a typed token struct is a value cascade, and the post can say that plainly instead of pretending nothing flows down the tree.

## Conclusion

The research moves the thesis from "style sheets are the wrong kind of reuse" to a sharper claim the evidence actually supports: style sheets bundle two mechanisms, *value inheritance* and *selector-driven rule matching*, and the industry has kept the first in every system it built while removing the second from every system it could. Lie's negotiation needed both because three strangers had to agree on one document; a product team needs only the first because it is one party with many artefacts. The cascade's remaining legitimate home is the user tier, a party the web has and Roblox does not, and the post is on firm ground if it says so rather than pretending user overrides are obsolete.

The implication for Roblox specifically is that StyleSheets are a transitional form, not a destination. They imported the web's container (tags, selectors, pseudo-instances) to carry values (tokens, states, queries, transitions) that every other engine delivers through a prefab or component primitive, and the community's complaints track that mismatch precisely: tags are praised for nothing and criticised for their count, tokens and queries are praised and criticised for nothing. If Roblox ships the component primitive the author asked for in 2024, the selector half of StyleSheets has no remaining job and the token half becomes the "widely shared parameters" the Perfection draft is about to describe.
