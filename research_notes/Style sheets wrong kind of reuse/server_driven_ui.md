# Server-driven UI (SDUI) architectures: how big apps split "server sends arrangement" from "client owns styled components"

Research date: 2026-10-08. Scope: primary engineering-blog / vendor-doc sources on SDUI, with attention to the server/client styling boundary, vocabulary, versioning, and any explicit HTML/CSS analogies.

## Key question 1: Case studies — what the server controls vs. what the client owns

### Takeaway
Across Airbnb, Netflix, Yelp, Shopify, Spotify, Nubank and Lyft, the stable pattern is: the server sends an ordered tree of *named* sections/components plus their data and actions; the client maps each name to a locally implemented design-system component that owns rendering. Styling in the payload, where present at all, is expressed as enumerated variants ("primary", "heading1-bold", a token name), not raw colours/fonts; the exceptions (Netflix "fine-grained", Nubank's scripted Catalyst, Yelp's `background_color` token) are explicitly described by their authors as trade-offs or points of tension.

### Cited Findings

**Airbnb — Ghost Platform (GP), 2021**
- Airbnb describes GP as "a unified, opinionated, server-driven UI system that enables us to iterate rapidly and launch features safely across web, iOS, and Android." — [Airbnb Engineering, "A Deep Dive into Airbnb's Server-Driven UI System", Ryan Brooks, June 2021](https://medium.com/airbnb-engineering/a-deep-dive-into-airbnbs-server-driven-ui-system-842244c5f5) (via search snippet; post not directly fetchable)
- The server's reach, in Airbnb's words: "Everything from the screen's layout, how sections are arranged in that layout, the data displayed in each section, and even the actions taken when users interact with sections is controlled by a single backend response across our web, iOS, and Android apps." — quoted in [InfoQ, "Airbnb's Server-Driven UI Platform", Sergio De Simone, 15 Jul 2021](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)
- GP "includes native frameworks for all supported platforms and provides a common collection of sections, layouts, and actions"; the data layer is Viaduct, "a GraphQL-based data layer, as a unified data-service mesh to provide responses and strongly typed models across all platforms." — [InfoQ](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)
- Three element types: **Sections** ("self-contained groups of UI components"), **Screens** (decide "where and how those sections appear"), **Actions** (user interaction). — [InfoQ](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)
- Each `Section` is wrapped in a `SectionContainer` carrying an `id`, a `sectionComponentType` enum (examples: `HERO`, `TITLE`, `PLUS_TITLE`), the section's data, and metadata/logging. InfoQ, quoting Airbnb: "each Section is wrapped through a SectionContainer which also contains a SectionComponentType. This enables the selection of alternative renderings of the same [section data]". `Section` is a GraphQL union (e.g. `HeroSection` with image URLs, `TitleSection` with `title`, `titleStyle`, optional click action). — [InfoQ](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)
- Screens: `ScreenContainer` holds `id`, `screenProperties` (e.g. popup vs. sheet) and a `layout` per form factor; layouts implement `ILayout`; `SingleColumnLayout` has `nav`, `main`, `floatingFooter` placements; `MultiColumnLayout` shown as placeholder. — [InfoQ](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)
- Styling in the schema: InfoQ notes "the only styling reference is the `TextStyle` type used by `TitleSection`. No broader styling approach is explained." — [InfoQ](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)
- Secondary summary of the split: "GP responses are split into sections and screens. Where sections define the more detailed components of a page and screens defining the general layout." — [Scrums.com newsletter](https://www.scrums.com/blog/issue-3-react-web-native-server-driven-ui-cloud-gaming) (secondary)
- Airbnb's earlier design-language work: the DLS article at airbnb.design now redirects to airbnb.com and could not be fetched; no DLS/Epoxy source was obtained (see Gaps).

**Lyft — Bikes & Scooters SDUI (2021–22) and LPL design system**
- Lyft's Bikes and Scooters team started in 2018 with "Server Supplemented UI" (initially called "capabilities"): the server "configure[d] small, contained parts of a screen while the client kept control of the overall layout", returning "booleans, localized strings, image URLs, and UI elements like alerts, prompt panels, and labels". Teams later moved to full SDUI for "handling business complexity, increasing release velocity, and staffing and building features more flexibly." — [Lyft Engineering, "The Journey to Server Driven UI At Lyft Bikes and Scooters"](https://eng.lyft.com/the-journey-to-server-driven-ui-at-lyft-bikes-and-scooters-c19264a0378e) (via search snippets; post not fetchable; the "Core Primitives of SDUI" section was not retrievable)
- Lyft Product Language (LPL) is Lyft's shared design system across Android, iOS and web "supported by a Figma component library"; "Each platform implements the design system separately". "the team behind Lyft's server-driven UI framework also adopted Compose" because, per Lyft, "Compose will automatically detect changes, so no additional client code is required to support dynamic content." — [Android Developers Blog, 24 Oct 2022](https://android-developers.googleblog.com/2022/10/lyft-reduced-their-code-for-ui-components-using-jetpack-compose.html)
- Lyft's Live Activities post says the team "cloned and simplified its existing SDUI models to fit a 4KB payload limit" and used protobuf. — [Lyft Engineering, "Crafting Seamless Journeys with Live Activities"](https://eng.lyft.com/crafting-seamless-journeys-with-live-activities-abe82e98546f) (via search snippet)

**Spotify — Hub Framework (iOS, 2016–2018, deprecated)**
- Self-description: "a toolkit for building native, component-driven UIs on iOS" that "also makes it easy to build backend-driven UIs"; content can be "defined in code, running locally in the application, or through JSON that is provided by a backend system"; you can "change your UI and its content directly from the backend." Components "define a rectangle on the screen in which anything can be rendered" and "can be reused and rearranged in any way, and render any model." Used in production for Browse, Running, Party and Genre pages. — [spotify/HubFramework README](https://github.com/spotify/HubFramework)
- The JSON vocabulary is semantic, not stylistic. A component model has `component.id` ("The identifier (`namespace:name`) of the component to use to render the model"), `component.category`, `text.title` ("The title that the component should display"), `text.subtitle`, `text.description`, `images.main/background/icon/custom`, `target`, `metadata`, `logging`, `children`, and `custom` ("Dictionary used to provide an extension point for component authors"). "The page does not mention style or raw styling properties." — [Hub Framework JSON programming guide](https://spotify.github.io/HubFramework/json-programming-guide.html)
- Component categories are enumerated (`Banner`, `Card`, `Carousel`, `Header`, `Row`); a factory registered per namespace "returns `nil` for names it doesn't support"; guidance: "if there is a way to use the properties already available on HUBComponentModel, that is definitely preferred" over `customData`. — [Hub Framework component programming guide](https://spotify.github.io/HubFramework/component-programming-guide.html)
- No post on engineering.atspotify.com about the successor "backend-driven" Home architecture was found; only job ads referencing "Home Config" and a "generative UI platform" (see Gaps).

**Yelp — CHAOS + Cookbook + Konbini (2024–2026)** — the strongest "design system is the vocabulary" case
- Motivation: "Yelp develops two major applications, Yelp & Yelp for Business, for Web (Desktop & Mobile), iOS, and Android platforms. That's eight unique clients!"; prior per-team SDUI frameworks "were expensive to develop and maintain, and no single SDUI framework supported all our clients." CHAOS = "Content Hosting Architecture with Optimization Strategies", started late 2021. — [Yelp Engineering, "CHAOS: Yelp's Unified Framework for Server-Driven UI", Joshua Walstrom, 14 Mar 2024](https://engineeringblog.yelp.com/2024/03/chaos-yelps-unified-framework-for-server-driven-ui.html)
- Component modelling: "we modeled each component or action as a versioned REST object in JSON format" with a type string like `chaos.button.v1`; views/layouts stay GraphQL types (`ChaosSingleColumn`, `ChaosMobilePhoneScreen`); parameters are a stringified JSON object. Clients "keep internal component libraries and use factories keyed by component type to map CHAOS components to their own interfaces." Styling appears only as parameters such as `"style": "primary"`, `textStyle`, `textAlignment`. — [Yelp, Mar 2024](https://engineeringblog.yelp.com/2024/03/chaos-yelps-unified-framework-for-server-driven-ui.html)
- Backend vocabulary examples: `chaos.text.v1`, `chaos.illustration.v1`, `chaos.button.v1`, actions `chaos.open-url.v1`, `chaos.open-subsequent-view.v1`, containers (vertical/horizontal stacks), layouts (single-column, mobile layout with toolbar/footer). Text style is semantic: `"textStyle": "heading1-bold"`, `"textAlignment": "center"`; buttons `"style": "primary"`. The JSON-string approach "allows for rapid iteration on new elements or versions" while keeping the GraphQL schema stable. — [Yelp Engineering, "Exploring CHAOS: Building a Backend for Server-Driven UI", Jonathan Baird & Xin Shen, 8 Jul 2025](https://engineeringblog.yelp.com/2025/07/chaos-inside-yelps-sdui-framework.html)
- Design-system integration: Cookbook is "Yelp's cross-platform design system, maintained by the Design Systems team"; it exists because two apps × three platforms gives "six variations that are hard to keep unified" and it "helps ensure a component such as a button looks and behaves consistently across Android, iOS, and the Web." Konbini is "an auto-generated bridge library" — "a set of libraries that expose the Cookbook component interfaces to Python code" — generated from JSON interface definitions in a `component_interfaces` repo; one definition yields Kotlin, Swift, Python and TypeScript libraries. "When CHAOS was in the design phase, the team realized Cookbook would need to be extended to support an additional platform, Python/CHAOS." — [Yelp Engineering, "How Yelp Keeps Server-Driven UI Consistent Across Four Platforms", Radu Comaneci, 22 Apr 2026](https://engineeringblog.yelp.com/2026/04/keeping-server-driven-ui-consistent-across-platforms.html)
- What the Python server may say: it instantiates Cookbook components by name with parameters such as `text`, `style`, `on_click`, `size`, `background_color`; "Style and size are enumerated values (e.g., 'primary,' 'small'). Colors are referenced as named tokens." "Tokens are maintained in a separate repository by designers and provided as JSON." The client render function "maps the size parameter to platform-specific button variants". Feature teams should avoid customizing components "beyond the provided interfaces"; components "may vary slightly per platform due to native conventions". — [Yelp, Apr 2026](https://engineeringblog.yelp.com/2026/04/keeping-server-driven-ui-consistent-across-platforms.html)
- Caveat on raw values: tokens "are serialized as a name, and when exported, include a `raw_value` field with the actual value"; the article's wire examples are inconsistent (one shows only the token name, one includes RGBA) and "It does not explain which form clients receive in production." — [Yelp, Apr 2026](https://engineeringblog.yelp.com/2026/04/keeping-server-driven-ui-consistent-across-platforms.html)

**Shopify — Shop app Store screen (2022)**
- Server-side types: base `Section`, `ProductsSection` ("All products", "Best Sellers", "Trending"), `CollectionsSection`; layouts `GridLayout` (2×2 large / 3×3 medium blocks) and `ShelfLayout` (horizontal scroll, small/large blocks). Client: `ServerDrivenStoreScreen` → `StoreSectionContainer` → `ProductsSection` (renders `ProductGrid`/`ProductShelf`) or `CollectionsSection` (`CollectionShelf`). — [Shopify Engineering, "Implementing Server-Driven UI Architecture on the Shop App", Ashwin Narayanan, 22 Nov 2022](https://shopify.engineering/server-driven-ui-in-shop-app)
- Split: "Server controls: which sections appear, the layout type, display size, and per-merchant templates and experiments. Client controls: how components render, navigation callbacks…, and a default layout for each section." The server-driven approach "allows us to control which store sections we want to display for a merchant's store." The styling boundary is "not explicitly define[d]" — the server supplies layout and display-size properties; colours/typography are not mentioned as server-controlled. — [Shopify](https://shopify.engineering/server-driven-ui-in-shop-app)

**Netflix — UMA/CLCS notifications (2024) and coarse-grained page schema (2026)**
- "Netflix calls a notification UMA – Universal Messaging Alert", running on TV, web, iOS and Android; developers write notifications in JavaScript embedding CLCS components, "similar to React embedding HTML". Sample uses `Modal`, `VerticalStack`, `Text` with `typography` and `content` props. **"Netflix did not want to reinvent HTML for UMA, so they built CLCS as a wrapper around Hawkins"** (Hawkins = Netflix's design system). "The Netflix apps are responsible for the layout of notifications" (orientation, positioning, size); the server supplies content and logic. Only notifications are SDUI; the rest of the apps are native. — [InfoQ, "Netflix's server-driven UI…", Karsten Silz, 24 Jul 2024, on Christopher Luu's QCon London 2024 talk](https://www.infoq.com/news/2024/07/netflix-server-driven-ui/)
- Netflix 2026 philosophy slide: "Server-Driven UI: Server describes the page. Client renders it." Their chosen point on the spectrum is **"Coarse-Grained: Server decides WHAT, Client decides HOW"**, between "Client-Driven: Client owns schema" and "Fine-Grained: Server controls props" / "Thin Client: Server owns render". The slide contrasts payloads for "The Same Movie. Four Different APIs.": coarse-grained sends `"entity": {"id": "80189025"}, "treatment": "BillboardEntityTreatment"` ("Server sends a signal"), whereas fine-grained sends `"layout": {"titleSize": 48, "padding": "24px 32px", "ctaStyle": "PRIMARY"}` ("Server controls visual props and layout"), and thin-client is literally `<HTML>…</HTML>`. — [Netflix, "Screens on Shuffle: Netflix's journey of SDUI Schema", Sreekanth Ramakrishnan, GraphQLConf 2026 slides](https://hosted-files.sched.co/graphqlconf2026/cb/Screens%20on%20Shuffle.pdf)
- Vocabulary: Page → Section → Entity; "Treatments: The Signal on Top". Same section (Carousel) with section treatments STANDARD / GAMES / COMING_SOON; same entity (video) with entity treatments `Boxshot` ("Portrait poster, title below"), `StandardBillboard` ("Wide hero art, synopsis, button"), `CharacterCircle`, `RankedBoxshot`. "Three Independent Axes": section type, section treatment, entity treatment. Schema: `interface BaseSection { id: ID!, sectionTreatment: SectionTreatment }`, `interface Entity { entityId: ID!, entityTreatment: EntityTreatment }`. — [Netflix GraphQLConf 2026 slides](https://hosted-files.sched.co/graphqlconf2026/cb/Screens%20on%20Shuffle.pdf)
- Netflix's client-foundations team roadmap describes "a flexible spectrum of server-driven rendering, from coarse-grained control through to fine-grained UI control, or none at all." — [Netflix job posting (via search)](https://www.workingnomads.com/jobs/software-engineer-5-android-netflix) (job ad; weak source)

**Nubank — Bonafont (templated) → Catalyst (scripted), 2025–26**
- Four generations: client-driven; basic SDUI via BFF ("server controls content and order"); templated framework "Bonafont" (server-selected templates with variables/actions — "mostly always in an almost fits stage"); scripted framework "Catalyst", "a small tree-walk interpreter" in Flutter evaluating expressions that return UI components. It "powers almost every new flow and more than half of the application". Design system relationship: "we have the whole design system for Nubank implemented as UI components" and "We can just create anything by just leveraging the design system dynamically." "The only time I need a client release right now is when I want to define one of those constants [e.g. navigate], or when a new UI component is needed." — [InfoQ presentation, "Mobile Server-Driven UI at Scale", Rafael Ring (Nubank), QCon London](https://www.infoq.com/presentations/mobile-server-driven-ui-scale/); abstract at [QCon London](https://qconlondon.com/presentation/apr2025/mobile-server-driven-ui-scale)

**Careem — AppEngine (2025)**
- "Instead of hardcoding UI elements in the app, AppEngine dynamically delivers UI layouts from the backend." The app "doesn't contain business logic, making it easier to maintain and keeping it highly responsive." Product Ops uses a self-serve tool; failover keeps one failing part from breaking the app. No component vocabulary, styling boundary or design-system relation is described (only configurable Ramadan "themes"). — [Careem Engineering, 22 Mar 2025](https://engineering.careem.com/tech/posts/app-engine-server-driven-ui)

**Meta / Instagram — Bloks**
- Only secondary sources: The New Stack headline "Instagram Lite Is No Longer a Progressive Web App — Now a Native App Built with Bloks"; its body (via search snippet, citing TechCrunch and reverse-engineer Jane Manchun Wong) says Bloks "moves most of Instagram Lite's application logic to the server-side and renders it as a native application", compared "to how React Server Components works", with a custom engine rendering "layouts sent from the server in a custom format rather than HTML or JS". — [The New Stack](https://thenewstack.io/instagram-lite-is-no-longer-a-progressive-web-app-now-a-native-app-built-with-bloks/) (body not fetchable; secondary)

**Faire**
- Faire reports SDUI "eliminating 90% of the rendering logic across its three clients, resulting in a reduction of 65% in lines of code." — [Faire Engineering, "Transitioning to Server-Driven UI"](https://craft.faire.com/transitioning-to-server-driven-ui-a76b216ed408) (via search snippet; Medium-hosted, not fetchable)

### Inferences
- Where companies publish their schema (Airbnb, Netflix, Yelp, Shopify, Spotify), the server-side nouns are *document-like*: Page/Screen → Section → Component/Entity, with enumerated "component type"/"treatment"/"style" variants. This is the "paragraphs and headings made of design-system components" structure the author wants to argue for.
- The clearest institutional evidence that "the design system is the SDUI vocabulary" is Yelp (Konbini literally generates the server's Python API *from* the design system's component interfaces, so the server can only say what Cookbook can render), Netflix CLCS ("wrapper around Hawkins"), Nubank ("whole design system… implemented as UI components"), and Lyft (SDUI framework built atop LPL).
- Netflix's 2026 "coarse-grained" slide is the most explicit statement from a major company that the *right* place on the spectrum is "server decides what, client decides how", and it puts "Server controls visual props and layout" (fine-grained) and HTML (thin client) on the far side of the line.

## Key question 2: Vocabulary, semantic tokens vs raw styling, versioning / unknown-component handling, and claims about restyling without server changes

### Takeaway
Payload vocabularies are overwhelmingly enumerated (component type + variant + token name); the only systems that ship raw visual props are the ones their own authors present as the "fine-grained"/"thin client" extreme or as over-configurable messes. Versioning is handled by (a) client-declared capabilities (Netflix), (b) per-platform/app-version gating on the server (Yelp, Netflix), (c) component-level version suffixes with migration shims (Yelp), (d) client-side default/fallback renderings (Shopify, Spotify, Netflix baseline components, Adaptive Cards). No company source found makes the explicit claim "we redesigned our design system without touching server content"; the closest are Yelp's token/Konbini pipeline and Adaptive Cards' "host owns look and feel" principle.

### Cited Findings

**Vocabulary / semantic variants (no raw styling)**
- Yelp buttons: `"style": "primary"`; text `"textStyle": "heading1-bold"`; sizes "small"; colours "referenced as named tokens"; "Tokens are maintained in a separate repository by designers and provided as JSON." — [Yelp, Apr 2026](https://engineeringblog.yelp.com/2026/04/keeping-server-driven-ui-consistent-across-platforms.html); [Yelp, Jul 2025](https://engineeringblog.yelp.com/2025/07/chaos-inside-yelps-sdui-framework.html)
- Netflix coarse-grained payload: `"treatment": "BillboardEntityTreatment"` — "Server sends a signal" — vs fine-grained `"titleSize": 48, "padding": "24px 32px"`. — [Netflix GraphQLConf 2026](https://hosted-files.sched.co/graphqlconf2026/cb/Screens%20on%20Shuffle.pdf)
- Spotify Hub Framework JSON: title/subtitle/description/images/target/custom — no style keys. — [Hub JSON guide](https://spotify.github.io/HubFramework/json-programming-guide.html)
- Shopify: layout enums (`GridLayout` 2×2/3×3, `ShelfLayout` small/large) rather than pixel values. — [Shopify](https://shopify.engineering/server-driven-ui-in-shop-app)
- Apollo's SDUI guidance (vendor, but widely used as the GraphQL SDUI reference): "In server-driven UI (SDUI), the client's goal is to handle pixels, not data." "Rather than returning hex codes in a request for something like badge color, it's best to use a design system that operates on tokens so you can change the business logic behind color choices more easily." Example badge `theme` values: `brand-color:primary`, `brand-color:warning`. "While the choice of what grid format to use or spacing should be kept on the client side, the API should control other choices, like whether a badge should be red or green based on user state or data." The mapping from GraphQL types to native components "is called a component registry." — [Apollo GraphOS docs, "Server-driven UI client design"](https://www.apollographql.com/docs/graphos/schema-design/guides/sdui/client-design)
- Apollo schema-design page: types prefixed `UI` (`UIApp`, `UIScreen`, `UIComponent` interface); "Different devices (for example, mobile, web, Roku, Apple TV) may require different UI layouts or components" handled via a `UIDeviceType` enum and contracts "to remove UI components that are unrelated to the target platform from your schema." — [Apollo, "Server-driven UI schema design"](https://www.apollographql.com/docs/graphos/schema-design/guides/sdui/schema-design)

**Versioning and unknown components**
- Netflix (2026): **"Page Capabilities: The Contract — NOT THIS: API Versioning / Schema Introspection. THIS: Capabilities. Client declares what it can render. Server returns only that. No versioning. No negotiation."** Schema: `input PageCapabilities { sectionTypes: [String!]!, sectionTreatments: [String!]!, entityTreatments: [String!]! }`. Type lifecycle: `@experimental` ("Opted-in clients only. Gated by capabilities") → stable ("Ships to all clients") → `@deprecated` ("Still returns data. Old clients remain safe") → removed ("Zero active traffic. No breakage occurred") — "one direction: forward". — [Netflix GraphQLConf 2026](https://hosted-files.sched.co/graphqlconf2026/cb/Screens%20on%20Shuffle.pdf)
- Netflix UMA (2024): "Older clients keep asking for the components they know, so they ignore new features. New components declare a fallback built from CLCS baseline components. 'Baseline components are guaranteed to be there.'" Apps send app version and device info in request headers. — [InfoQ, Jul 2024](https://www.infoq.com/news/2024/07/netflix-server-driven-ui/)
- Yelp: versions in type ids (`chaos.button.v1` → adding `style` created `chaos.button.v2`); a YAML file gates "which component and action types each platform and app version may use" (`web: true`; `start: <app version>` per mobile platform). — [Yelp, Mar 2024](https://engineeringblog.yelp.com/2024/03/chaos-yelps-unified-framework-for-server-driven-ui.html). "Registers" list the components/actions a client must support; "If no register qualifies, the feature is omitted." — [Yelp, Jul 2025](https://engineeringblog.yelp.com/2025/07/chaos-inside-yelps-sdui-framework.html). Konbini: each client has a spec file with supported component versions; client sends e.g. `android@23.0` and "the backend chooses a component version that client supports"; breaking change ⇒ major bump (0.8 → 1.0); a generated `migrate` method backports newer models to older spec versions (default throws). — [Yelp, Apr 2026](https://engineeringblog.yelp.com/2026/04/keeping-server-driven-ui-consistent-across-platforms.html)
- Shopify: "Each section has a client-defined default layout, which renders when the client gets a layout type it doesn't recognize"; "Making layout a property of a section means new display styles don't require new section types"; unknown *section types* are mentioned as a challenge but not solved in the post. — [Shopify](https://shopify.engineering/server-driven-ui-in-shop-app)
- Spotify Hub: `component.category` is "Used to perform sensible fallbacks for older versions of the application that might not support the requested component"; a `HUBComponentFallbackHandler` protocol exists. — [Hub JSON guide](https://spotify.github.io/HubFramework/json-programming-guide.html)
- Apollo's reference registry simply throws `'Unknown Type Returned!'` for an unregistered `__typename`. — [Apollo client design](https://www.apollographql.com/docs/graphos/schema-design/guides/sdui/client-design)
- Nubank: a client release is needed only "when a new UI component is needed" or to define a new native constant. — [InfoQ Nubank talk](https://www.infoq.com/presentations/mobile-server-driven-ui-scale/)

**Claims about restyling / redesign without touching content**
- Adaptive Cards (the clearest explicit statement, see Q4): the same payload "will look and feel like a Skype card. When that same payload is sent to Microsoft Teams, it will look and feel like Microsoft Teams." — [Microsoft Learn, Adaptive Cards overview](https://learn.microsoft.com/en-us/adaptive-cards/)
- Yelp: tokens "provide predefined values so teams don't have to choose them for each component"; the article "makes no claim that redesigns can ship without server changes." — [Yelp, Apr 2026](https://engineeringblog.yelp.com/2026/04/keeping-server-driven-ui-consistent-across-platforms.html)
- Netflix 2024 regret list: Luu "wished he had finished the baseline components sooner, along with a formal testing strategy, closer alignment with design system partners, and alignment with platforms on templates." — [InfoQ, Jul 2024](https://www.infoq.com/news/2024/07/netflix-server-driven-ui/)
- Open edX mobile tokens proposal (not SDUI, but the same argument): "colors are hard-coded into the app and changing the palette requires a new release to the app stores… This causes drift between web and mobile, inconsistent or broken dark mode, and accessibility regressions"; "If tokens are unavailable or the feature is disabled, the app falls back to its built-in color configuration." — [Open edX proposal](https://openedx.atlassian.net/wiki/spaces/OEPM/pages/5333811250/Proposal+Design+Tokens+for+Open+edX+Mobile+Branding+Theming+Dark+Mode)

### Inferences
- Because every published payload names a *variant* ("primary", "heading1-bold", "BillboardEntityTreatment", "GridLayout") rather than a value, a design-system restyle (new primary colour, new heading typography, new billboard art direction) is by construction a client-only change in these systems. The author can argue this from the schemas; no company has written the sentence "we restyled without touching the server" — that should be presented as an inference, not a quote.
- Netflix's capability negotiation and Yelp's app-version gating mean the server can *add* vocabulary safely, but *renaming/removing* vocabulary is still a coordinated change — the equivalent of HTML element deprecation, not of swapping a stylesheet.

### Gaps
- No source found with an explicit, quotable "we shipped a visual redesign to SDUI screens with zero backend changes" claim. The nearest evidence is structural (token-based payloads) plus Adaptive Cards' host-styling guarantee.
- Airbnb's and Lyft's fallback/versioning rules remain unverified (Medium blocked).

## Key question 3: Published lessons and failures — when the server controlled too much

### Takeaway
The published failure modes are consistent: payloads that carry visual props or scripting become "overly configurable messes" / a "god-protocol" (Thoughtworks), "every minor visual variation became a new treatment… schema and design drifted apart" (Netflix), "we're building a scripting language" (Nubank), and templates that "almost fit" (Nubank). The recommended correction is always toward semantic signals resolved by the client's design system and tighter schema–design alignment.

### Cited Findings
- Thoughtworks Technology Radar: in Oct 2022 the authors "experienced some horrendous, overly configurable messes" that didn't deliver the promised benefits; in Apr 2026 (Trial) proprietary frameworks can produce "horrendous, overly configurable messes" and the approach "needs a strong business case and disciplined engineering to avoid a 'god-protocol'"; recommended "only for highly dynamic parts of an app, not as a replacement for all UI development"; Mar 2022: "Note, we're not recommending this approach for all UI development". — [Thoughtworks Radar, "Server-driven UI"](https://www.thoughtworks.com/radar/techniques/server-driven-ui)
- Netflix 2026, "What Worked. What We Learned": WORKED — "Ship in minutes. Not releases. Features, layouts, and experiments go live the moment the server returns them. No app store. No coordination." LEARNING — **"Schema should tie into design. Every minor visual variation became a new treatment. Near-duplicates compounded. Schema and design drifted apart."** Applicability: fits "Multiple platforms / High experiment volume / Long release cycles / Repeating discovery patterns"; think twice for "Highly stateful UI / One-off surfaces / Single platform / **Fine-grained layout control**". Closing: "The schema is the product roadmap. Evolve it deliberately." — [Netflix GraphQLConf 2026](https://hosted-files.sched.co/graphqlconf2026/cb/Screens%20on%20Shuffle.pdf)
- Netflix 2024 costs: "Higher upfront framework investment, the need to stay backward compatible, harder offline support and debugging, and some developers dislike non-native development." — [InfoQ, Jul 2024](https://www.infoq.com/news/2024/07/netflix-server-driven-ui/)
- Nubank: templates left teams needing "that extra mile", and each gap forced an app release; actions "started to grow out of control"; "we're building a scripting language. We're not dealing with actions anymore"; composing behaviour was "much harder than composing UI over those templates"; complex expressions create large payloads; teaching a custom DSL company-wide took "major effort". — [InfoQ Nubank talk](https://www.infoq.com/presentations/mobile-server-driven-ui-scale/)
- Yelp lesson on schema shape: explicit GraphQL types per component "were hard to maintain" (clients can't partially select a button's fields; detecting new fields required parsing the query AST), so they moved components to versioned JSON objects while keeping views/layouts in GraphQL "which change less often". — [Yelp, Mar 2024](https://engineeringblog.yelp.com/2024/03/chaos-yelps-unified-framework-for-server-driven-ui.html)
- Shopify: the team chose to build Shop-Store-specific SDUI components rather than reuse another team's "to control data types"; a faulty section can be pulled server-side "without waiting for an app release". — [Shopify](https://shopify.engineering/server-driven-ui-in-shop-app)
- Lyft's intermediate "Server Supplemented UI" (server configures "small, contained parts of a screen while the client kept control of the overall layout") was later superseded by full SDUI. — [Lyft Bikes & Scooters post (via search snippet)](https://eng.lyft.com/the-journey-to-server-driven-ui-at-lyft-bikes-and-scooters-c19264a0378e)
- Practitioner guidance (vendor blog): each client component should "handle its own rendering and styling, acting on server instructions rather than the server dictating every detail." — [Nativeblocks, "Best practices and common pitfalls"](https://nativeblocks.io/blog/best-practices-and-common-pitfalls/) (vendor; weak)
- Adaptive Cards design principle, written as a lesson: "It is easier to add later than it is to live with a mistake… It is always easier to add a property than to live with a legacy we wish we didn't have to support." ("When in doubt, keep it out") — [Microsoft Learn](https://learn.microsoft.com/en-us/adaptive-cards/)

### Inferences
- Netflix's "every minor visual variation became a new treatment" is the SDUI analogue of class-name explosion: once the vocabulary admits presentational distinctions, it grows without bound. Their fix ("schema should tie into design") is to make the vocabulary *be* the design system's vocabulary — the same move Yelp made mechanically with Konbini.
- Nubank's trajectory (templates → actions → scripting language) is the cautionary case for pushing *behaviour* server-side; it is orthogonal to styling but the author can use it to show that "server sends structure, client owns everything else" is the stable equilibrium.

### Gaps
- No source uses the literal phrase "styling leaked into the schema". The explicit anti-hex guidance comes from Apollo (vendor docs), not from a company post-mortem.
- The Nubank transcript does not discuss styling at all.

## Key question 4: The HTML/CSS analogy — SDUI as "semantic markup", design systems as the vocabulary

### Takeaway
Several primary sources make the document analogy directly: Netflix "did not want to reinvent HTML" so wrapped its design system; Adaptive Cards is explicitly "Semantic instead of pixel-perfect", "Card Authors own the content, Host App owns the look and feel", and models itself on Markdown; DEPT compares SDUI to "how HTML works, but at a higher level"; Netflix's spectrum slide places raw HTML at the "thin client" extreme. No source mentions CSS Zen Garden.

### Cited Findings
- Netflix: "Netflix did not want to reinvent HTML for UMA, so they built CLCS as a wrapper around Hawkins" (design system); developers embed CLCS components "similar to React embedding HTML". — [InfoQ, Jul 2024](https://www.infoq.com/news/2024/07/netflix-server-driven-ui/)
- Netflix spectrum: "Thin Client — `<HTML> … </HTML>` — Server owns render" vs their "Coarse-Grained — Server decides WHAT, Client decides HOW". — [Netflix GraphQLConf 2026](https://hosted-files.sched.co/graphqlconf2026/cb/Screens%20on%20Shuffle.pdf)
- Adaptive Cards principles: **"Semantic instead of pixel-perfect — We have striven as much as possible for semantic values and concepts as opposed to pure pixel-perfect layout. Examples of semantic expression show up in colors, sizes, and in elements like FactSet and ImageSet. These all allow the host application to make better decisions about the actual look and feel."** **"Card Authors own the content, Host App owns the look and feel — The card authors own what they want to say, but the application displaying it owns the look and feel of the card in the context of their application."** "Keep it simple, but expressive — … we don't want to build a UI framework. The goal is to create an intermediate layer which is 'expressive enough' in the same way Markdown is expressive enough for documents." Goals include "Purely declarative - No code is needed or allowed" and "Automatically styled - To the Host application UX and brand guidelines". For experience owners: "Consistent user experience - You guarantee a consistent experience for your users, because you own the style of the rendered card." — [Microsoft Learn, Adaptive Cards overview (page updated Dec 2025)](https://learn.microsoft.com/en-us/adaptive-cards/)
- Adaptive Cards HostConfig: "`HostConfig` is a cross-platform configuration object that specifies how an Adaptive Card Renderer generates UI." The host sets `fontFamily`, `fontSizes` (small/default/medium/large/extraLarge), `fontWeights` (lighter/default/bolder), `foregroundColors` (default/accent/dark/light/good/warning/attention, each with default+subtle), `spacing` (small…extraLarge, padding), `containerStyles` (default/emphasis), `imageSizes` (small/medium/large). Card authors can only name these semantic buckets; the host supplies the values. `allowCustomStyle` is a host switch. — [Microsoft Learn, HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- DEPT (Dutch): "In zekere zin kun je dit vergelijken met hoe HTML werkt, maar dan op een hoger niveau" ("In a sense you can compare this with how HTML works, but at a higher level"); "niet de client beslist hoe de domeinobjecten worden weergegeven, maar de server"; recommends agreeing component names via "een style guide of brandbook". — [DEPT, "Build better experiences with server-driven UI", 1 Nov 2021](https://www.dept.global/insight/build-better-experiences-with-server-driven-ui)
- Apollo: the client is "a component registry" that maps schema types to "React, SwiftUI, Jetpack" components; "handle pixels, not data". — [Apollo client design](https://www.apollographql.com/docs/graphos/schema-design/guides/sdui/client-design)
- Yelp's Konbini makes the design system the literal API: it "expose[s] the Cookbook component interfaces to Python code" and is regenerated from JSON component-interface definitions on every commit. — [Yelp, Apr 2026](https://engineeringblog.yelp.com/2026/04/keeping-server-driven-ui-consistent-across-platforms.html)
- Nubank: "We can just create anything by just leveraging the design system dynamically." — [InfoQ Nubank talk](https://www.infoq.com/presentations/mobile-server-driven-ui-scale/)
- Tutorial-level claim (secondary): teams should "have a Design Language/Design System in place before building a server-driven UI API, so the server and clients stay in sync on which components can be rendered". — [GeekyAnts, "Codegen in a Server-Driven UI"](https://geekyants.com/blog/codegen-in-a-server-driven-ui) (vendor; weak)
- Secondary definitional contrast the author may find useful: "semantic markup in HTML [means] using tags to indicate what content is, rather than how it should look". — [Medium/Codex, "Semantic UI doesn't even use semantic markup"](https://medium.com/codex/semantic-ui-doesnt-even-use-semantic-markup-7d311da1530e) (opinion piece)

### Inferences
- Adaptive Cards is the most quotable formalisation of the author's thesis: content author = server, host = client/design system, with a *finite semantic palette* (good/warning/attention, small/large, emphasis) instead of a cascade. Its "Markdown is expressive enough for documents" line is an explicit document analogy.
- Netflix placing `<HTML>` at the "server owns render" extreme is a useful nuance: engineers see HTML(+CSS-in-the-payload) as *more* server control than SDUI, which supports the argument that SDUI is HTML's *semantic* half without its stylesheet half.

### Gaps
- No source compares SDUI to CSS Zen Garden or uses "semantic markup" to describe SDUI payloads; those framings are the author's own.
- Judo's SDUI explainer (judo.app/blog) and Ryan Brooks'/Josh Holtz' explainers were unreachable (TLS failure / Medium 403).

## Key question 5: JSON UI schemas that constrain styling to a palette — Slack Block Kit, Adaptive Cards, Discord

### Takeaway
Slack Block Kit, Discord components and Adaptive Cards all expose a closed vocabulary of blocks/elements whose only "styling" knobs are semantic enums (Slack `primary`/`danger`; Discord Primary/Secondary/Success/Danger/Link/Premium; Adaptive Cards good/warning/attention etc.), and the host application decides the actual appearance.

### Cited Findings
- Slack: "The Block Kit UI framework is built with *blocks*, *block elements* and *composition objects*." Blocks are visual layout components; block elements are interactive parts; composition objects supply text/options. — [Slack docs, Block Kit](https://docs.slack.dev/block-kit/)
- Slack block catalogue (display names): Actions, Alert, Card, Carousel, Container, Context, Context actions, Data table, Data visualization, Divider, File, Header, Image, Input, Markdown, Plan, Rich text, Section, Table, Task card, Video. "Blocks are a series of components that can be combined to create visually rich and compellingly interactive messages." Limits: "up to 50 blocks in each message, and 100 blocks in modals or Home tabs." — [Slack docs, Blocks reference](https://docs.slack.dev/reference/block-kit/blocks/)
- Slack button `style`: only `primary` and `danger` (plus default). "`primary` gives buttons a green outline and text, ideal for affirmation or confirmation actions"; "`primary` should only be used for one button within a set"; "`danger` gives buttons a red outline and text, and should be used when the action is destructive"; "Use `danger` even more sparingly than `primary`"; "If you don't include this field, the default button style will be used." — [Slack docs, Button element](https://docs.slack.dev/reference/block-kit/block-elements/button-element/)
- Discord button styles: Primary ("The most important or recommended action in a group of options"), Secondary ("Alternative or supporting actions"), Success ("Positive confirmation or completion actions"), Danger ("An action with irreversible consequences"), Link ("Navigates to a URL"), Premium ("Purchase"). Guidance: use styles "to create a hierarchy", "only one `Primary` button per group"; "The page doesn't specify colors for any style." — [Discord developer docs, Components reference](https://docs.discord.com/developers/components/reference)
- Adaptive Cards: "platform-agnostic snippets of UI, authored in JSON… the JSON is transformed into native UI that automatically adapts to its surroundings"; "Adaptive Cards are always native and blend seamlessly into the surrounding UI"; "Safe - Content is delivered in safe payloads so you don't have to open up your UI framework to raw markup and scripting." — [Microsoft Learn](https://learn.microsoft.com/en-us/adaptive-cards/); host-level knobs enumerated in [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)

### Inferences
- These three schemas are useful to the author as "SDUI for third parties": they prove the semantic-palette approach scales to untrusted authors, which is a stronger constraint than a company's own backend. The Slack guidance ("only one primary per set") shows the host also encodes *design rules*, not just colours.

### Gaps
- Slack's docs do not contain an explicit sentence that "Slack controls the look"; it is implicit in the closed `style` enum. Figma Code Connect was not researched (no bearing on the styling-boundary question found in time).
