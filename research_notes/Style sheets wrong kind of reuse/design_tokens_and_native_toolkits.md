## Key Question 1: Origin and definition of design tokens; spec status; how major design systems define what counts as a token

### Takeaway
"Design tokens" were coined at Salesforce by Jina Anne and Jon Levine (Theo, Salesforce's token transformer, was created on GitHub in February 2014), and are consistently defined as *named entities that store visual design attributes* used in place of hard-coded values. The W3C Design Tokens Community Group shipped its first stable format (2025.10) on 28 October 2025: explicitly *not* a W3C standard, but a "Final Community Group Report" intended for implementation. Across Material 3, Primer, Atlassian, Spectrum, Carbon and Polaris the tokenised categories converge on colour, typography, spacing/size, shape/radius, elevation/shadow, opacity, motion (and occasionally breakpoints/z-index). Layout, structure, and component anatomy are conspicuously not tokens anywhere.

**What major design systems say a token is, and which categories**
- **Material 3 (material-web docs):** "Reference tokens hold concrete values, such as a hex color, pixel size, or font family name." "System tokens define decisions and roles that give the design system its character" (`--md-sys-color`, `--md-sys-typescale`, `--md-sys-shape`). "Component tokens are design attributes assigned to elements. They can be system tokens or concrete values." "Each component token maps to a system token, which has a concrete reference value." "On the web, design tokens are CSS custom properties and can be scoped with CSS selectors." Material Web does not yet support `--md-sys-shape` or `--md-sys-motion` tokens. — [material-web theming README](https://raw.githubusercontent.com/material-components/material-web/main/docs/theming/README.md); [material-web.dev Material theming](https://material-web.dev/theming/material-theming/)
- **Material 3 naming** (secondary summary; the m3.material.io page is JS-rendered and could not be fetched): names start with the system name, then tier abbreviation (ref/sys/comp), then a descriptive role; tokens can resolve to different values by context (form factor, dark theme, dense layout, RTL). — [Material 3 token structure summary, designsystemscollective](https://www.designsystemscollective.com/the-token-structure-that-survives-five-products-google-uses-it-too-c480e864ef64); official page: [m3.material.io/foundations/design-tokens/overview](https://m3.material.io/foundations/design-tokens/overview)
- **Primer (GitHub):** "Base color tokens are the lowest level tokens and map directly to a raw value." "They are **only** to be used as a reference for functional and component/pattern tokens." "Base color tokens don't respect color modes and should never be used directly in code or design." "Functional color tokens reference base color tokens under the hood, and respect color modes." "Component/pattern color tokens may reference both base and functional tokens … These tokens are limited and functional tokens are preferred." "Every pattern in Primer is built to work across all color modes out of the box." — [primer.style UI color system](https://primer.style/foundations/color/overview)
- **Primer primitives package:** raw values for color, spacing, typography; nine themes including dark, dark-dimmed, dark-high-contrast, dark-colorblind, dark-tritanopia; compiled with Style Dictionary; a mode "can be created by only including the changes from the main mode, which Primer calls overrides." (search snippet) — [primer/primitives](https://github.com/primer/primitives)
- **Atlassian:** "Design tokens are a single source of truth to name and store design decisions for Atlassian app experiences." Tokens are "name and value pairings that represent small, repeatable design decisions." Categories: color (text, links, icons, backgrounds, borders, blankets, charts, skeleton loaders), elevation ("perceived surface level and shadow"), opacity, space, typography (family, size, weight, line height); border/radius/motion exist as nav links. Naming = foundation.property.modifier, e.g. `color.icon.success`. "A theme is a collection of token values designed to achieve a certain look or style." "Themes are how we switch color schemes and styles everywhere using a single set of tokens." "Non-color themes are also possible" (compact/comfortable density, reduced motion, custom typography). Choose tokens "based on meaning where applicable, not specific values" — matching by lookalike colour "can break the experience in other themes." — [atlassian.design Design tokens](https://atlassian.design/foundations/tokens/design-tokens/)
- **Adobe Spectrum:** tokens are "a methodology for expressing reusable design decisions as structured data." Types: primitive/global ("Primitive tokens define the available values in the design language", e.g. `blue-800`, `corner-radius-75`), alias ("A token that references another token instead of a final value"), semantic (purpose-named, e.g. `accent-background-color-default`), component-specific (e.g. `tooltip-maximum-width`). Worked chain: `blue-900` → `accent-color-900` → `accent-content-color-default`; "Each layer adds additional context without redefining the underlying value." "Design tokens enable alignment, automation, learnability, and multi-platform fidelity." — [spectrum.adobe.com Design tokens](https://spectrum.adobe.com/page/design-tokens)
- **Spectrum Design Data spec:** a token must not include both a value and a `$ref`; a `component` name field marks component-scoped tokens; aliases "participate in the cascade without their target values being checked during specificity or layer comparison." (search snippet) — [Spectrum Design Data token format](https://opensource.adobe.com/spectrum-design-data/spec/token-format); [cascade spec](https://opensource.adobe.com/spectrum-design-data/spec/cascade)
- **Carbon (IBM):** Theme = "A collection of visual attributes assigned to the tokens in order to create a specific aesthetic." Token = "A role-based identifier that assigns a value to a theme. Tokens are universal and never change across themes." Role = "The systematic usage(s) of a token. Roles cannot be changed between themes." "Each theme shares the same variables and roles, with only the value changing for each individual theme." Categories on the themes page: color, spacing, typography, "global" (component-specific and general variables controlling e.g. "layer usage or border width"). — [carbondesignsystem.com Themes overview](https://carbondesignsystem.com/elements/themes/overview/)
- **Polaris (Shopify):** consumed as CSS custom properties with a `--p` prefix ("signal[s] that these variables are Polaris variables"), e.g. `var(--p-color-bg-surface)`, or as JS `tokens.color['color-bg']`; token metadata carries a description, e.g. `color-bg`: "For use as a background color, in components such as Page and Frame backgrounds." — [polaris-tokens README](https://raw.githubusercontent.com/Shopify/polaris/main/polaris-tokens/README.md). Polaris v12 "includes a style uplift for all of our components, updates to our token values, and a new web font, Inter," and introduced primitive and semantic token layers. (search snippet) — [Polaris v12 release notes](https://polaris.shopify.com/previous-releases/version-12) (page now redirects to shopify.dev)
- **Salesforce Lightning (platform docs):** "Design tokens" are the named entities Lightning components reference for styling; see the platform intro. — [Salesforce Lightning: Design Tokens intro](https://developer.salesforce.com/docs/atlas.en-us.lightning.meta/lightning/tokens_intro.htm)

### Inferences
- Across six systems the tokenised set is tightly bounded: colour, type, space/size, radius/shape, elevation/shadow, opacity, motion. None tokenises layout structure, component anatomy, slot composition, or selectors. That bounded set is exactly the list the blog argues is "worth sharing."
- The DTCG's type list (color, dimension, fontFamily, fontWeight, duration, cubicBezier, number + composites) is itself a formal statement of what the industry agreed is shareable as data, with no concept of selectors, specificity or cascade in the format.
- Primer's "never use base tokens directly" and Atlassian's "choose by meaning, not value" rules are both about keeping the component ↔ token relationship deterministic under theme swap.

## Key Question 2: "Semantic / alias / component" tiers — how design systems describe layering, and whether the layering lives in components rather than cascading rules

### Takeaway
Every major system describes a 2–3 tier chain (primitive/reference/global → semantic/system/functional/alias → component) where each tier *references* the one below by name, not by cascade. The component tier is explicitly optional and "limited" (Primer), "a smaller role" (Spectrum), or "a dark art" to be used sparingly for theming (Curtis). In code, the binding of a component to its tokens is expressed in the component's own definition (default parameters in Compose, `var()` in a component's own CSS, `ButtonDefaults`), not by external selector rules.

### Cited Findings
- Spectrum chain: component-specific `drop-zone-background-color` → alias `accent-visual-color` → alias `accent-color-800` → global `blue-800` (#147AF3). "new components should combine alias and component-specific tokens." (search snippets) — [Spectrum design tokens](https://spectrum.adobe.com/page/design-tokens)
- Material: "Each component token maps to a system token, which has a concrete reference value." Component tokens are overridden on the element: `md-filled-button.error { --md-filled-button-container-color: var(--md-sys-color-error); }` — [material-web theming](https://material-web.dev/theming/material-theming/)
- Primer: three tiers; "Component/pattern color tokens … are limited and functional tokens are preferred." — [primer.style](https://primer.style/foundations/color/overview)
- Mozilla Foundation's documentation names the tiers explicitly: Tier 1 "Global/Core/Fundamental" (context-agnostic primitives), Tier 2 "Alias/Semantic/Theme" (inherit from Tier 1, describe intended use), Tier 3 "Component" (often inherits Tier 2, tied to specific component values or overrides). (search snippet) — [Mozilla Foundation design tokens](https://foundation.mozilla.org/docs/design/websites/design-tokens/)
- Brad Frost's "Subatomic Design Tokens" course (chapter 2, 2024–25) describes "a three-tiered token system" of ingredients available to the system, mapping of ingredients to UI roles, and reserved tokens for component-specific and special cases; applied to color, typography, spacing, border, shadow, animation, with composite tokens for typography, shadow and animation. (search snippet) — [bradfrost.com, Subatomic Design Tokens course chapter 2](https://bradfrost.com/blog/post/subatomic-design-tokens-course-chapter-2-now-live/)
- Criticism of the third tier: a CodePen writer (Chris Coyier, "Chris' Corner: Tokens", 30 June 2025) said the component tier leads to "a real blowing up of how many custom properties are in use, to the point that it feels overly cumbersome." (search snippet) — [blog.codepen.io](https://blog.codepen.io/2025/06/30/chris-corner-tokens/)
- Nathan Curtis, "Component Tokens as a Dark Art" (SmashingConf Antwerp, 29 Oct 2024): "A taxonomy of generic and semantic concepts is very often enough to spread purposeful visual decisions across a UI component catalog." "Many design systems can live forever without nary a component-level design token." Once intent shifts to offer themes, "that clean token taxonomy can drift into a messy, complicated, and darker place." He shares experiences "extending token taxonomies with just enough component-level design tokens." (search snippets of the session listing) — [SmashingConf Antwerp 2024, Nathan Curtis](https://smashingconf.com/antwerp-2024/speakers/nathan-curtis)
- Jetpack Compose component API guidelines (AndroidX repo): components should "Prefer explicit inputs and configuration options in your components, such as function parameters." Theme CompositionLocals "should be read in default expressions, not inside the component body"; components are "discouraged to read this `CompositionLocal` in implementation." Grouped style objects like `ButtonColors` "must be passed as an explicit parameter for the component." Avoid "grab-bag style parameters and classes, akin to `ComponentStyle` or `ComponentConfiguration`." Defaults should live in a public `ComponentDefaults` object. — [androidx compose-component-api-guidelines.md](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/docs/compose-component-api-guidelines.md)
- Android's official XML→Compose migration mapping: `Widget.Material3.Button` style → `Button(colors = ButtonDefaults.buttonColors(...))`; `TextAppearance.Material3.BodyMedium` → `TextStyle` in `Typography(bodyMedium = ...)`; "Styles have no **direct** equivalent in Compose - instead styles are passed as: parameters or modifiers to composables … or by creating layered, reusable composable variations with the defined style." For `style="@style/MyPrimaryButton"`: "don't try to replicate the style inline. Instead, suggest creating a specific composable" `MyPrimaryButton(onClick = { ... })`. — [developer.android.com, Migrate XML themes to Compose](https://developer.android.com/develop/ui/compose/designsystems/views-to-compose)
- Flutter: "Material components typically depend exclusively on the colorScheme and textTheme." Component themes (`ButtonThemeData`, `CardThemeData`) are typed fields on `ThemeData`, e.g. `cardTheme`: "The colors and styles used to render Card." — [api.flutter.dev ThemeData](https://api.flutter.dev/flutter/material/ThemeData-class.html)
- Material You codelab: "Tokens act as a bridge between an element's assigned role and the chosen color value for a role." "The mapping system assigns a tone to each element in a component." — [Google codelab, Visualizing dynamic color](https://codelabs.developers.google.com/visualize-dynamic-color)

### Inferences
- In every native toolkit surveyed, the "component tier" is not a token file at all: it is the component's own typed default (`ButtonDefaults.buttonColors`, `CardThemeData`, `ComponentDefaults`), i.e. the component *owns* its mapping from semantic tokens to its parts. The web systems emulate this with per-component custom properties set in the component's own stylesheet.
- The repeated advice that the component tier is optional/limited supports the thesis that the shared contract is the semantic tier, and that anything more specific belongs with the component.

## Key Question 3: How native toolkits do theming without a cascade (SwiftUI, UIKit UIAppearance, Jetpack Compose, Flutter, Android View system)

### Takeaway
SwiftUI, Compose and Flutter all use the same shape: a typed theme object pushed down the tree through an environment/inherited-value mechanism (`EnvironmentValues`, `CompositionLocal`, `InheritedWidget`), read by the component itself, with no selectors, no specificity and no per-property cascade. Compose's docs explicitly say XML styles "have no direct equivalent" and discourage overusing implicit `CompositionLocal` because it "makes a composable's behavior harder to reason about." UIKit's `UIAppearance` is the exception that proves the rule: a selector-like, containment-matched proxy whose precedence is the *reverse* of CSS and which is widely documented as confusing.

### Cited Findings

**SwiftUI (Environment + ViewModifier)**
- Apple's `EnvironmentValues` reference page is JS-rendered and returned no body; propagation semantics are documented in secondary sources: a parent's `.environment(\.cardElevation, 12)` modifier "applied once to the VStack and inherited by every child automatically"; lookup "checks the current view's environment, then walks up the ancestor chain until a value is found"; when no ancestor injected a value, "SwiftUI returns defaultValue" from the `EnvironmentKey`. (search snippets) — [developerinsider.co, Custom Environment Values](https://developerinsider.co/how-to-create-custom-environment-values-in-swiftui/); [Medium/intive, Theming SwiftUI applications](https://medium.com/intive-developers/theming-swiftui-applications-412b0221c8cf); [Apple docs EnvironmentValues](https://developer.apple.com/documentation/swiftui/environmentvalues)
- Apple Developer Forums thread distinguishes direction: preference keys are "for propagating values from a child view to its parent," while environment flows parent→child. (search snippet) — [Apple Developer Forums thread 724170](https://developer.apple.com/forums/thread/724170)

**UIKit UIAppearance (the "cascade-ish" outlier)**
- Mattt (NSHipster, 11 Mar 2013, reviewed 2015): "UIAppearance is a protocol that returns a proxy that will forward any configuration to instances of a particular class." Only properties marked `UI_APPEARANCE_SELECTOR` work: "One major downside to UIAppearance's proxy approach is that it's difficult to know which selectors are compatible." Pre-iOS 7 the `id` return type meant no code completion, "a major source of confusion and frustration." — [nshipster.com/uiappearance](https://nshipster.com/uiappearance/)
- Chris Farber (Atomic Object, 16 Aug 2017) quoting Apple: "In any given view hierarchy, the outermost appearance proxy wins." UIKit picks "the partial ordering that is the first unique match when reading the actual hierarchy from the window down." The containment array is written innermost-first, "reversed" relative to CSS descendant selectors; "A rule for a higher-level container beats a rule for a nested one, even when the nested rule is more specific"; developers coming from CSS "usually guess wrong." — [spin.atomicobject.com, Understanding UIAppearance Container Hierarchies](https://spin.atomicobject.com/uiappearance-container-hierarchies/)
- "UIAppearance: Magic == Pain" (mulle-kybernetik, 2013): appearance values only reliable from `didMoveToWindow` onward, not `viewDidLoad`/`viewWillAppear:`, complicating Auto Layout. (search snippet) — [mulle-kybernetik.com](https://www.mulle-kybernetik.com/weblog/2013/uiappearance_magic_pain)
- dev.to (fmo91): customisations must happen before views enter a `UIWindow`; global appearance rules "can become an anti-pattern." (search snippet) — [dev.to, Forgotten UIKit gems: UIAppearance](https://dev.to/fmo91/forgotten-uikit-gems-uiappearance-4no5)
- Habr commenter: UIAppearance records invocations and replays them; calling the same setter twice runs both on real instances. (search snippet) — [habr.com](https://habr.com/ru/articles/453126/comments/)
- iOS 7-era performance: certain appearance setters were slow due to method swizzling (SGVAppearanceProxy workaround). (search snippet) — [cocoapods.org SGVAppearanceProxy](https://cocoapods.org/pods/SGVAppearanceProxy)

**Jetpack Compose (MaterialTheme / CompositionLocal)**
- Anatomy of a theme: theme subsystems are classes (`ColorScheme`, `Typography`, `Shapes`; custom `ColorSystem`, `TypographySystem`) annotated `@Immutable`, "implicitly provided to the composition tree as `CompositionLocal` instances. This allows theming values to be statically referenced in composable functions." The theme function "is the entry point and primary API" and uses `CompositionLocalProvider`; reading goes through an object like `Theme.colorSystem` whose getter is `LocalColorSystem.current`. — [developer.android.com, Anatomy of a theme in Compose](https://developer.android.com/develop/ui/compose/designsystems/anatomy)
- CompositionLocal docs: "data flows down through the UI tree as parameters to each composable function. This makes a composable's dependencies explicit. However, this can be cumbersome for data that is very frequently and widely used, such as colors or type styles." "`CompositionLocal` is what the Material theme uses under the hood. `MaterialTheme` is an object that provides three `CompositionLocal` instances: `colorScheme`, `typography` and `shapes`." "We discourage _overusing_ `CompositionLocal` as it comes with some downsides." "`CompositionLocal` makes a composable's behavior harder to reason about. As they create implicit dependencies…" "there might be no clear source of truth for this dependency as it can mutate in any part of the Composition. Thus, debugging the app when a problem occurs can be more challenging as you need to navigate up the Composition to see where the `current` value was provided." "Avoid `CompositionLocal` for concepts that aren't thought as tree-scoped or sub-hierarchy scoped." "We recommend that you pass composables only what they need." — [developer.android.com, Locally scoped data with CompositionLocal](https://developer.android.com/develop/ui/compose/compositionlocal)
- Official migration guidance: "Styles have no **direct** equivalent in Compose"; "In XML you write `?attr/colorPrimary`. In Compose, you access theme values with `MaterialTheme.*`"; "XML uses named hex colors. Material 3 uses _semantic roles_ (e.g., `primary`, `onPrimary`, `surface`). Stop naming colors by their hex; name them by their role." — [developer.android.com, Migrate XML themes to Compose](https://developer.android.com/develop/ui/compose/designsystems/views-to-compose)
- Kotlin Slack (undated, community): "Styles for Views are in XML and Views work with them using styled attribute and theme API, Compose has nothing like that now." (search snippet) — [slack-chats.kotlinlang.org](https://slack-chats.kotlinlang.org/t/513988/flipping-it-on-it-s-head-to-have-this-idea-for-theme-synchro)
- **New (2026): the experimental Compose Styles API.** "a new paradigm for customizing or 'styling' elements and components in Jetpack Compose, which has traditionally been done through modifiers." A `Style` is "an interface that defines the appearance of a UI element, with a standard set of styleable properties." "It's similar to CSS styles and can be customized locally or through a theme." "Styles overwrite one another; setting a property twice (e.g., `background()`) results in a single, final value." "Styles run in the Draw and Layout phases of Compose, skipping out on the Composition phase." "Styles are not a replacement for modifiers, but they do act as a replacement for styling parameters, such as padding and colors." Status: "Styles are `@Experimental` and likely to change in upcoming releases, with Material support for Styles added in future releases." Requires foundation 1.12.0-alpha. — [developer.android.com, Styles in Compose](https://developer.android.com/develop/ui/compose/styles)
- Styles API skill page: styles are built with a builder referencing theme tokens directly (`background(colors.brandLight)`, `shape(shapes.extraLarge)`, `textStyle(typography.labelLarge)`, `disabled { background(colors.brandSecondary) }`); applied with `Modifier.styleable(styleState, JetsnackTheme.styles.buttonStyle, style)`; state handled via `StyleState` (`isEnabled`, `isPressed`), not selectors; "Expose this class through your custom theme with a static reference, don't use `CompositionLocals` here as it's not required." "does not support Material Design component Styles." Requires compileSdk 37, foundation 1.12.0-alpha01 or BOM 2026.04.01. — [developer.android.com, Jetpack Compose Styles API skill](https://developer.android.com/agents/skills/jetpack-compose/theming/styles/skill)

**Flutter (ThemeData / InheritedWidget)**
- "The static Theme.of method finds the ThemeData value specified for the nearest BuildContext ancestor." "This lookup is inexpensive, essentially just a single HashMap access." "Widget subtrees within an app can override the app's theme by including a Theme widget at the top of the subtree." "Theme.of can not see a Theme widget that is defined in the current build method's context" (use `Builder`). "Material components typically depend exclusively on the colorScheme and textTheme." — [api.flutter.dev ThemeData](https://api.flutter.dev/flutter/material/ThemeData-class.html)
- `InheritedWidget`: "Base class for widgets that efficiently propagate information down the tree." Consumers use `BuildContext.dependOnInheritedWidgetOfExactType`, which "will cause the consumer to rebuild when the inherited widget itself changes state." `Theme` "is implemented as a StatelessWidget that builds a private inherited widget." — [api.flutter.dev InheritedWidget](https://api.flutter.dev/flutter/widgets/InheritedWidget-class.html)

**Android View system (XML styles/themes)**
- Official docs: "A style is a collection of attributes that specifies the appearance for a single View." "A theme is a collection of attributes that's applied to an entire app, activity, or view hierarchy—not just an individual view." A theme "defines a collection of named resources that can be referenced by styles, layouts, widgets, and so on." (search snippets) — [developer.android.com Styles and themes](https://developer.android.com/guide/topics/ui/themes)
- Nick Butcher, "Android Styling: Themes Overlay" (Android Developers, Medium): "Setting a theme at any level in this tree doesn't replace the theme currently in effect, it overlays it." Attributes "specified in theme Foo but not specified in theme Bar will also be applied." (search snippets) — [medium.com/androiddevelopers themes overlay](https://medium.com/androiddevelopers/android-styling-themes-overlay-1ffd57745207)
- Nick Butcher, "Android Styling: Prefer Theme Attributes": "if you're tempted to write a direct resource reference, or a hardcoded value, in a layout or style, you should consider a theme attribute instead"; factoring colours to the theme "makes your layouts and styles more flexible, promoting reuse." (search snippets) — [medium.com/androiddevelopers prefer theme attributes](https://medium.com/androiddevelopers/android-styling-prefer-theme-attributes-412caa748774)
- Butcher's talk "Developing Themes with Style": "The Android Theming system is powerful but easy to misuse." (search snippet) — [speakerdeck.com/nickbutcher](https://speakerdeck.com/nickbutcher/developing-themes-with-style-7d0571e3-6008-4ec5-99c6-aa5669520124?slide=29)

### Inferences
- The distinction the blog needs: in SwiftUI/Compose/Flutter the *theme values* cascade (nearest-ancestor lookup of a typed object) but *rules* do not — there is nothing that says "all Buttons inside Cards are red". The only lookup is "what is the current value of this named key?", and the component decides what to do with it.
- Compose's own API guidelines say theme locals should be read in *default parameter expressions*, which is a precise statement of "the component owns its relationship to tokens, and the caller can see and override it."
- UIAppearance is the counter-example: it adds selector-like containment matching and inherits CSS's confusions (precedence, timing, discoverability) without CSS's tooling.
- The new Compose Styles API is worth watching: it adopts the *word* "style" and the "similar to CSS" analogy, but keeps the non-cascade model (last-writer-wins property objects, state via typed `StyleState`, no selectors); its motivation is performance (skipping composition) and reducing parameter sprawl, not shared selector rules.

## Key Question 4: Toolkits that DO have CSS-like style sheets, and how they are regarded (Qt QSS vs QML, JavaFX CSS, GTK 3/4 CSS, WPF/XAML, Unity USS/UXML, Unreal Slate/UMG, Godot Theme)

### Takeaway
Every CSS-like system surveyed documents the same two problems: (a) the cascade/inheritance either had to be *removed* (Qt: widgets "do not automatically inherit font and color"; WPF: inheritance is opt-in per property; USS: only a short list of text properties inherit) or produces origin/specificity surprises (JavaFX `-fx-base`, Qt "last rule wins among type selectors", WPF `StaticResource` vs `DynamicResource`); and (b) when the stylesheet is treated as a *theming* surface rather than a component-internal implementation detail, apps break (GNOME's "stop theming my app" position, Qt's "style sheets are a tool for prototyping and small, local adjustments"). The direction of travel in these ecosystems is towards exposing a small set of named variables (libadwaita CSS variables, USS variables, JavaFX looked-up colours, Qt Quick Controls `Material.accent`) — i.e. tokens — as the sanctioned theming API. Godot and Unreal UMG/Common UI never had a cascade: Godot uses typed theme items looked up by (name, data type, control type) with explicit per-control overrides; Common UI uses shared style *assets* referenced by widgets.

### Cited Findings

**Qt Widgets — Qt Style Sheets (QSS)**
- QSS is "heavily inspired by HTML Cascading Style Sheets (CSS) but adapted to the world of widgets." "Qt derives the effective style sheet from all of those that are set." With a style sheet active, `QWidget::style()` returns "a wrapper 'style sheet' style, _not_ the platform-specific style." — [doc.qt.io Qt Style Sheets](https://doc.qt.io/qt-6/stylesheet.html)
- Qt's own positioning (Qt 6 docs): "Style sheets are a tool for prototyping and for small, local adjustments"; for a production look it recommends a QStyle implementation or StyleKit. "Changing the style sheet at runtime can lead to inconsistent results." "Don't use this function to switch themes at runtime." Sheets override `QWidget::setFont`/`setPalette`. Security: "A malicious style sheet can cause Qt to read and display the contents of arbitrary local files." — [same](https://doc.qt.io/qt-6/stylesheet.html)
- Inheritance deliberately removed: "In classic CSS, when font and color of an item is not explicitly set, it gets automatically inherited from the parent. By default, when using Qt Style Sheets, a widget does not automatically inherit its font and color setting from its parent widget." Workaround: `QGroupBox, QGroupBox * { color: red; }`. Specificity quirk: "all Type Selectors have the same specificity, and the rule that appears last takes precedence." "the widget's own style sheet is always preferred to any inherited style sheet." Qt does not implement `!important`. — [doc.qt.io The Style Sheet Syntax](https://doc.qt.io/qt-6/stylesheet-syntax.html)
- Qt developer on the mailing list (2014): in widget style sheets "the only thing that is vaguely supported and working well this way … is setting the text foreground colour"; other properties tend to force "the style sheet to draw the widget as a Windows 95 control" because native styles draw with pixmaps. (search snippet) — [Qt development list, April 2014](https://lists.qt-project.org/pipermail/development/2014-April/016656.html)

**Qt Quick / QML (Qt Quick Controls styles)**
- Qt Quick Controls styling is not a stylesheet: "Qt Quick Controls comes with a selection of styles"; a style is selected at compile time (by import) or run time (`QQuickStyle::setStyle()`, `-style`, env var, config file). "Several styles expose APIs specific to that style" (Material/Universal attached objects), "only available when their style is actually selected." — [doc.qt.io Styling Qt Quick Controls](https://doc.qt.io/qt-6/qtquickcontrols-styles.html)
- Native styles cannot be customised: Qt 6.5 warning "The current style does not support customization of this control … Please customize a non-native style"; "the Windows and macOS styles don't support customisation"; in Qt 6 "the default style is chosen based on your platform," so many Windows users hit this. (search snippets) — [Qt interest list, April 2023](https://lists.qt-project.org/pipermail/interest/2023-April/039064.html)
- 2018 thread: a custom style "must do precise calculations for implicitHeight/implicitWidth, padding etc."; customising a built-in control instead inherits those from the base `Control`. Qt Quick Controls 1 Styles are "deprecated since Qt 5.12." (search snippets) — [Qt interest list, March 2018](https://lists.qt-project.org/pipermail/interest/2018-March/029607.html); [Qt Quick Controls 1 Styles](https://doc.qt.io/qt-5/qtquick-controls-styles-qmlmodule.html)

**JavaFX CSS**
- "based on the W3C CSS version 2.1" with some CSS 3 additions; property names "have been prefixed with a vendor extension of '-fx-'." Inheritance: only cursor, text alignment and font inherit by default; "Any property can be made to inherit by giving it the value 'inherit'"; "inheritance occurs from parent nodes in the scene‑graph." Looked-up colours: "With looked-up colors you can refer to any other color property that is set on the current node or any of its parents"; "Looked-up colors are not looked up until they are applied." Precedence: "a style from a user agent style sheet has lower priority than a value set from code, which has lower priority than a Scene or Parent style sheet"; "Inline styles have highest precedence." — [openjfx.io JavaFX CSS Reference Guide (21)](https://openjfx.io/javadoc/21/javafx.graphics/javafx/scene/doc-files/cssref.html)
- Cascade/origin pitfall (John Hendrikx, openjfx-dev, 9 July 2024): "The act of simply specifying -fx-base in your own AUTHOR stylesheet elevates hundreds of styles from Modena to AUTHOR level." "The style after all was specified by Modena, only its value came from another (higher priority) style sheet." Consequence: a label calling `setTextFill(Color.YELLOW)` only stays yellow if the author sheet overrides none of Modena's colours — "Overriding -fx-base in any way will result in the text fill of the label to be overridden." Also a JavaFX 21 shared-cache bug where a "SKIP" marker was wrongly reused. — [openjfx-dev, July 2024](https://mail.openjdk.org/pipermail/openjfx-dev/2024-July/047827.html)
- Performance bugs: "JavaFX CSS is applied redundantly leading to significant performance degradation" (JDK-8234898, backported to 8u251); nested containers reprocess the same leaf several times (JDK-8151756); a nested view went from instant on 8u162 to "at least three seconds" on 8u172 (JDK-8202022); each user-agent stylesheet add triggered full re-evaluation (JDK-8096378). (search snippets) — [JDK-8234898](https://bugs.openjdk.org/browse/JDK-8234898); [JDK-8151756](https://bugs.openjdk.org/browse/JDK-8151756); [JDK-8202022](https://bugs.openjdk.org/browse/JDK-8202022); [JDK-8096378](https://bugs.openjdk.org/browse/JDK-8096378)

**GTK 3/4 CSS and libadwaita**
- GTK4 CSS "focuses on listing supported CSS features and differences between Web CSS and GTK"; selectors "work very similar to the way they do on the web"; each node "has a name, a state and possibly style classes"; `:focus-within` is "Set on all ancestors of the focus widget, unlike CSS." Widgets document their own CSS node trees (e.g. `scale[.fine-tune]` → `trough`, `slider`). — [docs.gtk.org GTK4 CSS overview](https://docs.gtk.org/gtk4/css-overview.html)
- Tobias Bernard, "Restyling apps at scale" (15 Oct 2018): on GTK 3 "there is no clearly defined theming API"; "Visual design and interaction design are very closely linked"; "Real consistency can only happen by design"; "If you want to change how an app looks, you need a designer in the loop." Best practices like CSS variables and deriving colours "help, but they don't solve the problem." In comments he says a theming API would need to be "very limited (he cites macOS accent colors) or opt-in, or both," and that a colour API could allow modest customization such as changing the accent colour. — [blogs.gnome.org/tbernard](https://blogs.gnome.org/tbernard/2018/10/15/restyling-apps-at-scale/)
- GNOME Discourse, "Why and how libadwaita prevents theming?" (Sept 2023): Brage Fuglseth: "«Theming» is discouraged because it depends on a misuse of GTK's styling system to work"; it "has been done for so long that people don't remember that it's an unsupported hack." Danial Behzadi: "There is no 'theme' in GNOME world; just hacked alternative stylesheets." Jason Francis: libadwaita "does not actually prevent app themes through any technical means"; "using libadwaita means the libadwaita styles are a critical API dependency of the app"; `GTK_THEME` "is meant for testing, not for theming." Another participant: swapping the stylesheet an app depends on means "the widget might not be visible at all. The app becomes visually broken"; popular stylesheets "already have app-specific fixes in them." — [discourse.gnome.org thread 17079](https://discourse.gnome.org/t/why-and-how-libadwaita-prevents-theming/17079)
- The sanctioned replacement is variables: libadwaita exposes `--accent-bg-color`, `--accent-fg-color`, `--accent-color`, `--window-bg-color`, `--window-fg-color`, the GNOME palette (`--blue-1`…`--blue-5` etc.), dialog/sidebar/popover colours (added in 1.2–1.7). "Applications can override these colors by re-declaring them." Helper variables "should not be overridden." GTK3-style `@theme_bg_color` names "don't pick up overridden colors" and "it's recommended to avoid using these colors entirely." — [libadwaita CSS variables](https://gnome.pages.gitlab.gnome.org/libadwaita/doc/main/css-variables.html)

**WPF / XAML Styles and ResourceDictionary**
- "You can think of a Style as a convenient way to apply a set of property values to multiple elements." "Because styles are resources, they follow the same scoping rules as all resources." Implicit style: `<Style TargetType="TextBlock">` with no `x:Key` is "automatically applied to all TextBlock elements"; extension via `BasedOn="{StaticResource {x:Type TextBlock}}"`. Templates: "When you change the visual tree of a control, you must replace the entire ControlTemplate." Lookup: "The theme is the last place to look when searching for the style of an element. Typically, the search begins by walking up the element tree searching for an appropriate resource, then looks in the app resource collection and finally queries the system." Skinning: "Redefining these styles or other resources at the app level is the recommended approach for skinning an app." Built-in themes (Aero2, Fluent with light/dark, Luna, Classic) are swappable ResourceDictionaries; .NET 9 adds `ThemeMode="System"`. — [learn.microsoft.com WPF Styles and templates (updated 20 Mar 2026)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/controls/styles-templates-overview)
- Property inheritance is opt-in, not a cascade: "The WPF property system doesn't enable property value inheritance by default, and value inheritance is inactive unless specifically enabled in dependency property metadata." Enabled by default on e.g. `AllowDrop`, `FlowDirection`. "Making a property value inheritable affects performance, so only set Inherits to true if that feature is needed." Inherited values lose to "a locally set value, or a value obtained through styles, templates, or data binding." — [learn.microsoft.com Dependency property value inheritance](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/properties/property-value-inheritance)
- Pitfalls (community/GitHub): `StaticResource` references are "not reevaluated based on runtime behavior," so theme-dependent values must use `DynamicResource`; in theme dictionaries `DynamicResource` returns a `DeferredThemeResourceReference` that "gets inflated, frozen and cached," forcing `ComponentResourceKey`/`SystemColors` patterns (dotnet/wpf issue #9283); local keys silently shadow theme keys. (search snippets) — [dotnet/wpf issue 9283](https://github.com/dotnet/wpf/issues/9283); [Infragistics forum](https://es.infragistics.com/community/forums/f/ultimate-ui-for-wpf/93913/how-can-i-apply-ig-themes-to-microsoft-controls-and-apply-a-style?pi549=2)

**Unity UI Toolkit — USS / UXML / TSS**
- "USS files are text files inspired by Cascading Style Sheets (CSS) from HTML." "USS syntax is the same as CSS syntax, but USS includes overrides and customizations to work better with Unity." — [docs.unity3d.com USS](https://docs.unity3d.com/Manual/UIE-USS.html)
- Unity's manual: UI Toolkit is "inspired by standard web technologies"; "you can separate the structure, style, and behavior of your UI, similar to how you might with HTML, CSS, and JavaScript"; "USS supports a subset of standard CSS properties." (search snippets) — [Unity Manual, Introduction to UI Toolkit](https://docs.unity3d.com/6000.2/Documentation/Manual/ui-systems/introduction-ui-toolkit.html)
- Rationale from Unity staff (benoitd_unity, 22 July 2021): "Primarily because the two existing solutions can no longer scale with our ambitions, or the ones of our users"; goals include a single editor+runtime UI solution and "Better reusability, extensibility and style management." USS/UXML "bring familiarity, but they also allow us to build nicer authoring workflows on top of them," and are "implementation details." Pushback: april_4_short: "CSS barely meets the label of being a tool, let alone artist and designer friendly"; "No matter what you might think of CSS and its approaches, it will never be intuitive and instinctive." Supporter JohnPontoco: CSS is "the lingua franca of UI design for millions of developers already out there." — [discussions.unity.com, Why is Unity creating yet another UI System?](https://discussions.unity.com/t/why-is-unity-creating-yet-another-ui-system/850204)
- Inheritance is a short allow-list: the 2020.1 supported-properties page lists `color`, `font-size`, `-unity-font`, `-unity-font-style`, `-unity-text-align`, `visibility`, `white-space` as inherited; layout properties such as `align-content` are not. (search snippets) — [Unity 2020.1 USS supported properties](https://docs.unity3d.com/es/2020.1/Manual/UIE-USS-SupportedProperties.html); [USS properties reference](https://docs.unity3d.com/Manual/UIE-USS-Properties-Reference.html)
- USS variables: "When you update a variable, it updates all the USS properties that use it"; `var(--color-1, #FF0000)` fallback; `var()` can't nest in other functions and math on variables isn't supported; variables "work mostly the same way" as CSS. — [docs.unity3d.com USS custom properties](https://docs.unity3d.com/Manual/UIE-USS-CustomProperties.html)
- Theme Style Sheets: "Theme Style Sheet (TSS) files are regular USS files" that UI Toolkit "treats … as a distinct asset type and uses it for management purposes"; themes `@import url("unity-theme://default")`; "the current TSS overrides the imported style sheet"; docs say you "should use USS for styles" and reserve TSS for per-platform/per-language variants. — [docs.unity3d.com TSS](https://docs.unity3d.com/Manual/UIE-tss.html)
- Reception: The New Stack (May 2022) called the web-inspired approach unusual because "the games industry does not consider the web in itself to be suitable for low latency high-resolution tasks." (search snippet) — [thenewstack.io](https://thenewstack.io/how-to-use-the-ui-toolkit-to-develop-with-unity/). An indie devlog moved off UI Toolkit, calling it "relatively new and under-developed." (search snippet) — [beencha.itch.io devlog](https://beencha.itch.io/hand-companion/devlog/943542/quick-update-of-behind-the-scenes-replacing-ui-toolkit). A Dec 2024 r/Unity3D thread titled "UI Toolkit is unusable" exists but was not fetched. — [redlib mirror](https://redlib.ssps.io/r/Unity3D/comments/1hp50z0/ui_toolkit_is_unusable/m4gemp0/?context=3)

**Unreal Engine — Slate / UMG / Common UI**
- UMG styling is per-instance, no stylesheet: style options "can be assigned directly within UMG from the Details panel"; "Most Widgets will use the Normal, Pressed, Hovered, and Disabled States"; "For each state, you can set an Image (either a Texture or Material asset)." (search snippets) — [UCommonButtonStyle API](https://docs.unrealengine.com/4.27/API/Plugins/CommonUI/UCommonButtonStyle/index.html); [unreal-garden Common UI text](https://unreal-garden.com/tutorials/common-ui-text/); [Epic Parrot sample UI docs](https://dev.epicgames.com/documentation/unreal-engine/user-interface-for-parrot-in-unreal-engine)

**Godot — Theme resources (non-cascade theming)**
- Theme is "A resource used for styling/skinning Control and Window nodes." Six item data types: colors, constants, fonts, font sizes, icons, StyleBoxes. "A theme resource assigned to a control applies to the control itself, as well as all of its direct and indirect children" "as long as a chain of controls is uninterrupted." Variations: `set_type_variation()` "Marks theme_type as a variation of base_type"; "Variations can also be nested." Missing items fall back to engine defaults via `ThemeDB`. — [docs.godotengine.org Theme class](https://docs.godotengine.org/en/stable/classes/class_theme.html)
- GUI skinning guide: "each theme is separated into types, and each item must belong to a single type"; an item is identified by "its name, its data type and its theme type." Lookup order: (1) "Check for local overrides of the same data type and name"; (2) walk the control chain upward using type variation, class name, parent class names — "If there is no custom theme or it doesn't have the item, move to the parent control"; (3) "check the project-wide theme"; (4) "check the default theme." Local overrides affect "this control" and not "anything else in the project, including this control's children." The guide does say "UI themes are applied in a cascading manner (i.e. they propagate from parent controls to their children)." — [docs.godotengine.org GUI skinning](https://docs.godotengine.org/en/stable/tutorials/ui/gui_skinning.html)
- Type variations: a `GrayButton` variation "can replace some of the base type's styling and keep the rest" and "add properties the base type never defined"; per-control overrides "quickly become hard to manage when many controls need the same look." (search snippets) — [docs.godotengine.org Theme type variations](https://docs.godotengine.org/en/4.2/tutorials/ui/gui_theme_type_variations.html)

### Inferences
- The three ecosystems that imported CSS wholesale (Qt Widgets, JavaFX, GTK) each ended up either disowning the stylesheet as a theming API (Qt docs, GNOME) or documenting origin/cascade pathologies in the issue tracker (JavaFX). What survived as the supported surface is in every case a handful of named values — accent/window colours in libadwaita, `-fx-base` in JavaFX, attached `Material.*` properties in Qt Quick — which is to say, tokens.
- Unity's own staff describe USS as "implementation details" whose value is familiarity and tooling, not the cascade. Its variables + TSS mechanism is functionally a token layer.
- Godot's model is close to the blog's proposed ideal: a typed, name-keyed bag of values (colours, constants, fonts, sizes, icons, style boxes) looked up by component type, with overrides local to a control and no selector language at all. Note the docs still call the value propagation "cascading," so be careful with the word: it's nearest-ancestor *value* lookup, not rule matching.
- Common UI in Unreal demonstrates reuse without any stylesheet: styles are assets with per-state fields, and widgets reference them by object — the component "owns" its style type.

## Key Question 5: Writing that argues "tokens are the API/contract between design and components" or "the component owns its styles; tokens are the only shared contract"

### Takeaway
The explicit "tokens = contract/API" framing exists but is mostly in practitioner blogs; the strongest *official* versions are indirect: Carbon ("Tokens are universal and never change across themes… Roles cannot be changed between themes"), Atlassian ("Themes are how we switch color schemes and styles everywhere using a single set of tokens"), Primer ("never used directly in code"), and Compose's API guidelines (explicit parameters, theme read only in defaults). A notable dissent — "Design tokens aren't a contract" — argues that tokens only become a contract when there is a schema and enforcement, which the 2025.10 DTCG spec now partly supplies.

### Cited Findings
- Carbon: "Tokens are universal and never change across themes"; "Roles cannot be changed between themes"; "Each theme shares the same variables and roles, with only the value changing." — [carbondesignsystem.com Themes](https://carbondesignsystem.com/elements/themes/overview/)
- Atlassian: "Themes are how we switch color schemes and styles everywhere using a single set of tokens." — [atlassian.design](https://atlassian.design/foundations/tokens/design-tokens/)
- Primer: "Base color tokens don't respect color modes and should never be used directly in code or design." — [primer.style](https://primer.style/foundations/color/overview)
- Compose API guidelines: "Prefer explicit inputs and configuration options in your components, such as function parameters"; implicit inputs "add complexity to the components and every usage of it," with app-wide theming the narrow exception where flexibility is "usually worth the aforementioned downsides." — [androidx compose-component-api-guidelines.md](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/docs/compose-component-api-guidelines.md)
- Tobias Bernard (GNOME, 2018): CSS "is a large API used by both app developers and theme developers," so the two conflict; a theming API would have to be "very limited … or opt-in, or both." — [blogs.gnome.org/tbernard](https://blogs.gnome.org/tbernard/2018/10/15/restyling-apps-at-scale/)
- Jason Francis (GNOME Discourse, 2023): "using libadwaita means the libadwaita styles are a critical API dependency of the app." — [discourse.gnome.org](https://discourse.gnome.org/t/why-and-how-libadwaita-prevents-theming/17079)
- "Design tokens aren't a contract" (Design Systems Collective, member-only; author/date not retrievable): teams move from "here are my tokens" straight to "here are my components" without defining the contract; "In most systems, the tokens end up serving as the contract"; a real contract needs an authority such as a schema specifying required keys, types and constraints, and enforcement like compiler errors and failing CI; dark mode, high contrast and compact density "each act as a separate implementation that must satisfy the same interface." (search snippets) — [designsystemscollective.com](https://www.designsystemscollective.com/design-tokens-arent-a-contract-ac19e5e3afef)

- A design-system guidance doc places the contract one layer up: "component APIs are the contract between the design system and its consumers." (search snippet; low-authority) — [get-design-done guidance](https://cdn.jsdelivr.net/npm/@hegemonart/get-design-done@1.60.4/reference/design-system-guidance.md)

### Inferences
- The "tokens are the API" claim is better supported by what systems *forbid* (raw values in components, lookalike-colour matching, stylesheet replacement) than by explicit slogans. The blog can cite Carbon/Atlassian/Primer rules plus GNOME's "critical API dependency" as the industry converging on tokens-as-interface from both the design-system and the toolkit side.
- The DSC "not a contract" critique is compatible with the thesis: the DTCG format (typed values, `$ref` aliases, groups) is precisely the schema it asks for, and it contains no cascade.

### Gaps

- Nathan Curtis's EightShapes essays (403) would be the richest primary source for "options vs decisions"; not quotable here.

## Key Question 6: Theming case studies — re-skins via tokens alone (Atlassian dark mode, GitHub Primer themes, Shopify Polaris, Material You dynamic colour): what changed in components vs tokens

### Takeaway
Atlassian is the best-documented case: converting Jira's hard-coded hex values to ~300 tokens (90% automated) made dark and higher-contrast light themes buildable "quickly," while the long tail was non-token assets (1,200+ images across 60+ teams) and the Marketplace ecosystem. GitHub produces nine colour modes by swapping palettes in `@primer/primitives` under a fixed functional-token API; Material You swaps colour-role values at runtime so components "built to respond to dynamic color" need no change. Polaris v12 is the counter-example where the redesign changed token *values*, component styling *and* some component APIs together.

### Cited Findings
- **Atlassian:** Luke Ellery, 21 June 2023. Jira's colours "were hard-coded as hex values"; tokens are "a single source of truth for naming and storing design decisions (including color)"; an automation script converting hex to tokens "reduced 90% of the human work"; tokens let the team build a rough dark theme and a higher-contrast light theme quickly; "Images, icons, and illustrations don't use hex values, so they need separate alternative versions"; 1,200+ images across 60+ teams; ~350,000 users on the beta themes; 5,176+ alpha feedback items; shared components had been underused so the component library "had to grow alongside the token work." — [Atlassian blog, The story of dark theme](https://www.atlassian.com/blog/announcements/the-story-of-dark-theme)
- Atlassian colour system "codified into 300 design tokens," across 18+ products and 30,000 third-party apps; tooling claimed to save designers "over 4,000 hours" (self-reported). (search snippet) — [good-design.org, Atlassian's Colour System at Scale](https://good-design.org/?p=26314)
- Atlassian migration guidance: codemod "only provides token suggestions, so manual review is required"; "tokens are not a 1:1 match between the old and the new"; advice to "pick the best semantic match rather than matching colours by value"; `@atlaskit/tokens@1.0.0` removed deprecated tokens; opt-in theming API for Connect/Forge apps. (search snippets) — [atlassian.design Migrate to tokens](https://atlassian.design/foundations/tokens/migrate-to-tokens); [Atlassian developer community, tokens 1.0.0](https://community.developer.atlassian.com/t/upcoming-changes-in-design-tokens-1-0-0-action-required-soon-edit-now-live/66243)
- A Custom UI app's dark mode drifted when Atlassian changed the host dark palette but the host kept supplying old token values — an ecosystem-sync failure, light mode unaffected. (search snippet) — [Atlassian developer community thread 96092](https://community.developer.atlassian.com/t/custom-ui-app-dark-mode-design-tokens-dont-match-the-host-application/96092)
- **GitHub Primer:** Cole Bemis, 14 June 2022: palettes designed in Primer Prism, then "we export the palette from Primer Prism as a JSON object and add it to Primer Primitives, our repository of design tokens"; "We use pre-releases of the Primer Primitives package to test new color palettes on GitHub.com"; themes: dark, dark high contrast, light high contrast, colorblind. The article does not describe component changes. — [github.blog, Accelerating GitHub theme creation with color tooling](https://github.blog/news-insights/product-news/accelerating-github-theme-creation-with-color-tooling/)
- Primer supports nine themes; a mode "can be created by only including the changes from the main mode" (overrides); inverted neutral scales let themes "share many of the same functional color tokens without custom overrides." — [primer/primitives](https://github.com/primer/primitives); [primer.style color overview](https://primer.style/foundations/color/overview)
- **Material You:** Google: components are "built to respond to dynamic color, applying Material's new color roles in a consistent and comprehensive way"; "Designing for a color's role rather than the specific color is more fundamental with the introduction of dynamic color." (search snippets) — [material.io blog, Start building with Material You](https://material.io/blog/start-building-with-material-you); [Google codelab, Adding dynamic color](https://codelabs.developers.google.com/codelabs/apply-dynamic-color?hl=en). Codelab: key colours → tonal palettes → roles → "Tokens act as a bridge between an element's assigned role and the chosen color value for a role." — [Visualizing dynamic color codelab](https://codelabs.developers.google.com/visualize-dynamic-color). Chromium Android docs: the system overrides the role attributes with wallpaper-derived colours, and "any UI surface that references the color role attributes gets dynamically colored." (search snippet) — [chromium docs dynamic_colors.md](https://trac.godzil.net/starfive-tech/chromium.src/src/v106.0.5249.13/docs/ui/android/dynamic_colors.md)
- **Shopify Polaris v12 (counter-example):** "a style uplift for all of our components, updates to our token values, and a new web font, Inter"; introduced primitive and semantic token layers; "tokens may need to be updated to conform to the new language if you use them in stylesheets or as component props"; one spacing token moved from 20px to 16px in Card; release also lists "aligned component APIs." (search snippets) — [Polaris v12](https://polaris.shopify.com/previous-releases/version-12); [Polaris new design language beta](https://polaris.shopify.com/new-design-language). Shopify's app-home docs: legacy `@shopify/polaris` React components keep the old appearance; custom CSS that hardcodes token values "pins those rules to the old palette." (search snippet) — [shopify.dev Polaris 2.0](https://shopify.dev/docs/apps/build/app-home/polaris2.md)

### Inferences
- The clean "tokens only" re-skins (Atlassian dark/high-contrast, Primer's nine modes, Material You) are all *colour-mode* changes under a fixed role taxonomy; the moment the design language itself changes (Polaris v12, new type scale/density), component code and APIs move too. This matches Curtis's "once intent shifts to offer themes, the taxonomy drifts" warning and supports arguing tokens are the right unit for *theming*, not for *redesign*.
- Atlassian's long tail (images, illustrations, third-party apps) shows the boundary of what tokens can carry: anything not expressed as a named value had to be hand-remade.

### Gaps
- No Atlassian-authored statement quantifying how many component source files changed vs how many token values changed.
- GitHub has no public post-mortem on component changes for dark mode beyond the Primer Prism article.
- Polaris v12 release notes could not be fetched live (site redirects to shopify.dev); quotes are from search snippets.
