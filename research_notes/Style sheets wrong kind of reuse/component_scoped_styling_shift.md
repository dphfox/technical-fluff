# The industry shift from global cascading style sheets to component-scoped styling (2014–2026)

Scope note: these are research notes for a blog author arguing that modern tooling has converged on co-locating markup and style inside components, with only tokens/custom properties flowing through the cascade. Every claim below carries an inline source. Where I could not find a primary source, the item is listed under Gaps rather than asserted. Dates in sources are as printed on the page at time of fetch (Oct 2026).

## Key question 1: Timeline and rationale of scoping mechanisms (CSS Modules, styled-components/Emotion, Vue scoped, Svelte, Angular ViewEncapsulation, Shadow DOM, Tailwind, StyleX, Compiled, Linaria, vanilla-extract, Panda)

### Takeaway
From 2014 onward, essentially every mainstream styling tool independently chose "local by default" scoping of selectors to a component, and the authors' stated reasons are strikingly uniform: the global selector namespace, unpredictable override order ("specificity wars"), fear of deleting CSS, and the inability to reason about a component in isolation. The newer build-time tools (StyleX, Compiled, vanilla-extract, Panda, Linaria) keep the scoping but additionally remove runtime cost and make precedence deterministic.

**vjeux's seven problems (slide text, 2014)**

**styled-components / Emotion**
- Stoiber (2019): "Primarily, CSS-in-JS boosts my confidence."; "I can add, change and delete CSS without any unexpected consequences."; "My changes to the styling of a component will not affect anything else."; "we automatically sidestep common CSS frustrations such as class name collisions and specificity wars."; "Painless Maintenance: Never go on a hunt for CSS affecting your components ever again." — [mxstbr.com](https://mxstbr.com/thoughts/css-in-js)

**Vue single-file-component `<style scoped>`**
- "When a `<style>` tag has the `scoped` attribute, its CSS will apply to elements of the current component only."; "This is similar to the style encapsulation found in Shadow DOM. It comes with some caveats, but doesn't require any polyfills." Implemented via `data-v-xxxx` attribute selectors. — [vuejs.org](https://vuejs.org/api/sfc-css-features.html)
- The deliberate leak: "a child component's root node will be affected by both the parent's scoped CSS and the child's scoped CSS. This is by design so that the parent can style the child root element for layout purposes." — [vuejs.org](https://vuejs.org/api/sfc-css-features.html)
- Slot ownership: scoped styles "do not affect contents rendered by `<slot/>`, as they are considered to be owned by the parent component passing them in." — [vuejs.org](https://vuejs.org/api/sfc-css-features.html)
- Escape hatches: `:deep()`, `:slotted()`, `:global()` — [vuejs.org](https://vuejs.org/api/sfc-css-features.html)

**Svelte (Rich Harris)**
- 2017: "Everything in CSS is global."; namespacing conventions "mostly just increase your risk of RSI"; the "append-only stylesheet" where "there's no way of knowing which code can safely be removed." — [svelte.dev blog](https://svelte.dev/blog/the-zen-of-just-writing-css)
- "Your styles are scoped to the component. No more leakage, no more unpredictable cascade." The compiler can identify and remove unused styles; "the biggest problems with CSS can be solved without CSS-in-JS." — [svelte.dev blog](https://svelte.dev/blog/the-zen-of-just-writing-css)
- Current docs: scoped CSS "works by adding a class to affected elements, which is based on a hash of the component styles (e.g. `svelte-123xyz`)"; each scoped selector "receives a specificity increase of 0-1-0"; repeated occurrences use `:where(.svelte-xyz123)` "in order to not increase specificity further"; a component's `p` selector "will take precedence over a `p` selector defined in a global stylesheet" even if the global stylesheet loads later; `@keyframes` names are also scoped. — [svelte.dev docs](https://svelte.dev/docs/svelte/scoped-styles)
- Harris quoted by CSS-Tricks: a UI framework "that doesn't have a built-in way to add styles to your components is unfinished" — [CSS-Tricks (via search summary)](https://css-tricks.com/?p=297067)

**Angular ViewEncapsulation**
- "By default, Angular uses emulated encapsulation so that a component's styles only apply to elements defined in that component's template."; "the framework generates a unique HTML attribute for each component instance"; "This mode ensures that a component's styles do not leak out and affect other components." — [angular.dev](https://angular.dev/guide/components/styling)
- But: "global styles defined outside of a component may still affect elements inside a component with emulated encapsulation."; "Custom properties inherit down the DOM tree"; "Angular doesn't 100% guarantee that your component's styles will always override styles coming from outside it." — [angular.dev](https://angular.dev/guide/components/styling)
- `ShadowDom` mode: "Styles inside the shadow tree cannot affect elements outside of that shadow tree."; `None` mode: "Any styles associated with the component behave as global styles."; "The Angular team strongly discourages new use of `::ng-deep`." — [angular.dev](https://angular.dev/guide/components/styling)

**Shadow DOM**
- MDN: "the styles defined in the shadow DOM tree are scoped to that tree, so just as page styles don't affect elements in the shadow DOM, shadow DOM styles don't affect elements in the rest of the page." — [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)
- Eric Bidelman (web.dev): "Hands down the most useful feature of shadow DOM is scoped CSS:"; "Style rules don't leak out and page styles don't bleed in."; "Inheritable styles (background, color, font, line-height, etc.) continue to inherit in shadow DOM."; component authors "provide hooks (in the form of CSS custom properties) for users to override defaults." — [web.dev](https://web.dev/articles/shadowdom-v1)
- Miriam Suzanne: "Shadow-DOM was designed for the express purpose of encapsulating styles & behavior." but "Shadow-DOM is not designed for the common 'design system' approach" — [css.oddbird.net scope explainer](https://css.oddbird.net/scope/explainer/)

**Tailwind / utility-first**
- Wathan 2017: reframes "separation of concerns" as dependency direction; content-based naming gives "CSS that depends on HTML" ("your HTML is restyleable, but your CSS is not reusable"), pattern-based naming gives "HTML that depends on CSS"; "Trying to come up with these component names all of the time is exhausting."; "your CSS stops growing linearly with your project size."; aims at "keeping selector specificity low and making your CSS less dependent on your particular DOM structure." — [adamwathan.me](https://adamwathan.me/css-utility-classes-and-separation-of-concerns/)
- Tailwind docs: "Making changes feels safer — adding or removing a utility class to an element only ever affects that element, so you never have to worry about accidentally breaking something another page that's using the same CSS."; "Your code is more portable — since both the structure and styling live in the same place, you can easily copy and paste entire chunks of UI around"; "Your CSS stops growing"; "Styling things this way contradicts a lot of traditional best practices". — [tailwindcss.com](https://tailwindcss.com/docs/styling-with-utility-classes)
- Tailwind on the cascade: "When you add two classes that target the same CSS property, the class that appears later in the stylesheet wins. … In general, you should just never add two conflicting classes to the same element". Theme is delivered as CSS variables: "Many utilities in Tailwind are driven by theme variables, like `bg-blue-500`, `text-xl`, and `shadow-md`"; "Tailwind uses CSS variables to make it possible to compose these effects together". — [tailwindcss.com](https://tailwindcss.com/docs/styling-with-utility-classes)

**StyleX (Meta, 2023)**
- "StyleX is an expressive, deterministic, reliable, and scalable styling system for ambitious applications."; it "transforms, organizes, and optimizes styles into 'atomic' CSS class names" and "guarantees no specificity conflicts in the generated CSS."; "StyleX allows and encourages authoring styles in the same file as the component that uses them."; it is "aligned with the principles of encapsulation introduced by React Native's styling system." — [Introducing StyleX](https://stylexjs.com/blog/introducing-stylex/)
- "Thinking in StyleX" principles: Co-location ("The best and most readable way to write styles is to write them in the same file as the markup."; "StyleX is designed for authoring, applying, and reasoning about styles locally."); Deterministic resolution ("StyleX provides a completely predictable and deterministic styling system that works across files."; "When two styles set the same property, the last style applied wins."; "the more specific property wins (`margin-top` over `margin`) regardless of application order."); Encapsulation ("All styles on an element should be caused by class names on that element itself."; "CSS makes it very easy to author styles in a way that can cause 'styles at a distance'."; inheritance "is the _only_ form of style-at-a-distance that StyleX allows" and "the styles applied directly on an element always take precedence over inherited styles."); Shareable constants ("CSS class names, CSS variables, and other CSS identifiers are defined in a global namespace."); Framework-agnostic ("StyleX is a CSS-in-JS solution, not a CSS-in-React solution."); Single bundle ("Lazy-loading any CSS on a page triggers a recalculation of styles for the entire page."). — [Thinking in StyleX](https://stylexjs.com/docs/learn/thinking-in-stylex/)

**Atlassian Compiled**
- RFC-73 (2024-11-07): "The primary reason we are migrating to Compiled is to improve performance"; "Compiled's CSS generation creates static CSS at build time, reducing JavaScript bundle size and runtime overhead."; Compiled "is already in wide use across our products." FAQ warns of "potential style-ordering and selector-related issues where custom overrides or hard-coded selectors may change as a result." — [Atlassian RFC-73](https://community.developer.atlassian.com/t/rfc-73-migrating-our-components-to-compiled-css-in-js/85953)
- Project self-description (per docs index): "A high-performance, compile-time CSS-in-JS library for React that extracts styles into atomic CSS at build time."; "This approach reduces runtime overhead and minimizes CSS bloat through style re-use." — [Compiled docs (via Algolia index summary)](https://docsearch.algolia.com/mcp/docs/repo/atlassian-labs/compiled)

**Linaria (Callstack)**
- "Zero-runtime CSS in JS library."; "Write CSS in JS, but with zero runtime, CSS is extracted to CSS files during build"; "Dynamic styles will be applied using CSS custom properties (aka CSS variables) and don't require any runtime."; atomic styles available via `@linaria/atomic`. — [github.com/callstack/linaria](https://github.com/callstack/linaria)

**vanilla-extract (SEEK)**
- "Zero-runtime Stylesheets in TypeScript"; "Write type-safe, locally scoped classes, variables and themes, then generate static CSS files at build time."; "Don't ship a dynamic CSS engine to your users — ship regular CSS."; "Write maintainable CSS at scale without sacrificing platform features."; quoted tweet: "This is CSS Modules for the new decade" — [vanilla-extract.style](https://vanilla-extract.style/)

**Panda CSS (Chakra team)**
- "Panda is a styling engine. You write styles in TypeScript, and Panda generates plain atomic CSS at build time."; "You get the authoring experience of CSS-in-JS without shipping a style engine to your users."; "Generated styles use cascade layers, CSS variables, and modern selectors like `:where` and `:is`."; "CSS properties and design tokens are type-checked as you write them."; tokens compile to `var(--colors-white)`-style custom properties. — [panda-css.com](https://panda-css.com/docs/overview/why-panda)

### Inferences
- The rationales converge on one mechanism regardless of implementation (hashed class, attribute selector, shadow root, atomic class): make the selector's reach coextensive with the component. Every tool then re-adds a narrow, explicit hole for the two things that must cross the boundary: layout of a child's root (Vue) and theme values (custom properties in Tailwind, vanilla-extract, Panda, Linaria, Angular's note on custom properties).
- The second wave (StyleX, Compiled, vanilla-extract, Panda, Linaria, 2020–2025) did not re-litigate scoping; it treated scoping as settled and attacked runtime cost and non-deterministic precedence instead. StyleX's "last style applied wins" and Compiled/RNW "deterministic" resolution are a replacement for the cascade's source-order rule with an explicit, per-element merge.

## Key question 2: Facebook/Meta's experience (2014 seven problems → cx → StyleX)

### Takeaway
Meta's own account is a 11-year arc: Chedeau named the problems in 2014, the in-house `cx` system scoped names but stayed static, and StyleX (2023, default at Meta by 2025) resolved them by disallowing global and complex selectors, making property merge deterministic per element, compiling to atomic classes (CSS down ~80%), and permitting inheritance as the only remaining "style at a distance".

### Cited Findings
- Pre-StyleX facebook.com: "The average visitor to facebook.com would download tens of megabytes of CSS. Much of it unused."; "Usage of complex selectors would lead to conflicts or 'specificity wars'."; "Engineers would often resort to using `!important` or more complex selectors to solve their problems."; the old site "used something akin to CSS modules and suffered from various problems." Rebuilding facebook.com with React, "we knew we needed something better and built StyleX." — [Introducing StyleX, 2023-12-05](https://stylexjs.com/blog/introducing-stylex/)
- Meta Engineering 2025: the older `cx` system "remained limited to static styles defined in separate files"; "Developers increasingly wanted to colocate styles with component code."; "Serving CSS at such a scale resulted in collisions across bundles."; "Engineers resorted to complex selectors and !important tags, making styles brittle and hard to maintain."; "browsers were downloading hundreds of kilobytes of unused rules on every page load."; atomic classes "reduced CSS size by 80%." — [engineering.fb.com, 2025-11-11](https://engineering.fb.com/2025/11/11/web/stylex-a-styling-library-for-css-at-scale/)
- Meta 2025 on the cascade specifically: "You can think of the stylex.props function as a deterministic merge of style objects."; "The last style always wins!"; "Without additional handling, margin overrides margin-top here completely!" (shorthand/longhand hazard); "Global and complex selectors are disallowed to avoid styling at a distance."; global and element selectors are restricted "to minimize indirect styling and promote encapsulation of styles." — [engineering.fb.com](https://engineering.fb.com/2025/11/11/web/stylex-a-styling-library-for-css-at-scale/)
- Lineage: Meta credits "the lineage of systems like React Native and Linaria that continue to inspire our work" — [engineering.fb.com](https://engineering.fb.com/2025/11/11/web/stylex-a-styling-library-for-css-at-scale/); StyleX is "aligned with the principles of encapsulation introduced by React Native's styling system" — [stylexjs.com](https://stylexjs.com/blog/introducing-stylex/)
- Size numbers from the 2019 rebuild as reported by Lorber: "Their old site was 413Kb of CSS just for the landing page" and "Their new site is 74Kb for the whole site, including the dark mode"; CSS size "now follows a logarithmic curve" for both Twitter and Facebook; atomic CSS-in-JS avoids conflicts because "the last style declared in the markup always wins." — [sebastienlorber.com, 2020-04-27](https://sebastienlorber.com/atomic-css-in-js)
- 2014 origin: "We had to extend CSS and write a lot tooling for it." (local names via `/`, `cx()`, `cssVar`) — [Speaker Deck](https://speakerdeck.com/vjeux/react-css-in-js)
- Inheritance as the sole exception: "that is the _only_ form of style-at-a-distance that StyleX allows" and "the styles applied directly on an element always take precedence over inherited styles." — [Thinking in StyleX](https://stylexjs.com/docs/learn/thinking-in-stylex/)
- Variables remain the shared channel: "CSS class names, CSS variables, and other CSS identifiers are defined in a global namespace." (motivation for `defineVars`/shareable constants) — [Thinking in StyleX](https://stylexjs.com/docs/learn/thinking-in-stylex/)
- Adoption: StyleX "has since become the standard styling system across Meta products like Facebook, Instagram" and is "the default styling system at Meta." — [engineering.fb.com](https://engineering.fb.com/2025/11/11/web/stylex-a-styling-library-for-css-at-scale/)
- Outside Meta: Linear migrated styled-components → StyleX (finished Aug 2026; >1,000 PRs; ~5 months); reasons: "Runtime CSS-in-JS makes users pay for style generation and rule injection while the client renders."; `styled(Button)` "made it too easy to restyle a component from the outside."; "StyleX shifts style generation to build time and emits collision-free atomic classes."; results: 20–35% less main-thread work on view-heavy pages, ~30% faster navigation on a mid-tier machine, zero CSS rules injected during a page change. — [InfoQ, 2026-09-28](https://www.infoq.com/news/2026/09/linear-stylex-meta/)

### Inferences
- Meta's framing of the cascade is consistent across 2014 and 2025: the problem is not inheritance (kept) but selector-driven "action at a distance" and source-order-dependent resolution (removed). The one channel they explicitly keep open across components is variables (`defineVars`) plus inherited text properties, which is the "only variables cascade" thesis in Meta's own terms.
- The "413KB → 74KB" and "80%" figures are two reports of the same effect (atomic deduplication); treat them as consistent but from different authors/years.

### Gaps
- The 2023 StyleX launch post does not use the phrase "no cascade"; its claim is "no specificity conflicts in the generated CSS." The 2025 post has the "deterministic merge" language. A blog author should quote those rather than "no cascade".
- The Frank Yan React Conf 2019 talk is referenced by Lorber but I did not retrieve its transcript; the 413KB/74KB figures are second-hand via Lorber.
- The StyleX "Thinking in StyleX" page does not discuss Facebook scale explicitly.

## Key question 3: React Native and React Native for Web dropping the cascade/inheritance

### Takeaway
React Native removed general style inheritance on purpose (keeping it only inside nested `<Text>`), with a stated rationale of component isolation and implementation simplicity; React Native for Web carried the same restriction to the browser and replaced source-order resolution with deterministic, specificity-ordered atomic classes.

### Cited Findings
- RN docs contrast with the web: "On the web, the usual way to set a font family and size for the entire document is to take advantage of inherited CSS properties"; "In React Native, we are more strict about it: you must wrap all the text nodes inside of a `<Text>` component."; "You also lose the ability to set up a default font for an entire subtree." — [reactnative.dev/docs/text](https://reactnative.dev/docs/text)
- The limited exception: "React Native still has the concept of style inheritance, but limited to text subtrees." (nested `<Text>` inherits `fontWeight`, `color`, etc.) — [reactnative.dev/docs/text](https://reactnative.dev/docs/text)
- Stated rationale (developer): "React components are designed with strong isolation in mind: You should be able to drop a component anywhere in your application, trusting that as long as the props are the same, it will look and behave the same way. Text properties that could inherit from outside of the props would break this isolation." — [reactnative.dev/docs/text](https://reactnative.dev/docs/text)
- Stated rationale (implementor): "We do not need to have a `fontFamily` field on every single element, and we do not need to potentially traverse the tree up to the root every time we display a text node. The style inheritance is only encoded inside of the native Text component and doesn't leak to other components or the system itself." — [reactnative.dev/docs/text](https://reactnative.dev/docs/text)
- Recommended replacement for cascading typography: "create a component `MyAppText` that includes them and use this component across your app" and compose `MyAppHeaderText` from it — i.e. composition replaces inheritance. — [reactnative.dev/docs/text](https://reactnative.dev/docs/text)
- React Native for Web (Nicolas Gallagher): "Style resolution is deterministic and slightly different from CSS." The most precise style property takes precedence rather than source order; "This ensures that CSS order doesn't impact rendering"; styles map to "unique 'atomic CSS' class names"; "Class names are deterministic, which means that the resulting CSS and HTML is consistent across builds". — [necolas.github.io/react-native-web](https://necolas.github.io/react-native-web/docs/styling/)
- RNW inheritance: "React Native for Web adopts the same inheritance restrictions found in React Native"; "text style inheritance is only available within Text subtrees."; "The consequence of this is that default text styles cannot be set on View for an entire subtree."; "This approach means that components are designed with isolation in mind."; "This ensures that different design systems can co-exist on the same page and text styles are always encapsulated." — [necolas.github.io/react-native-web](https://necolas.github.io/react-native-web/docs/styling/)
- Gallagher (2017 Q&A) on why multi-platform components are hard: "a lot of that is due to the issues surrounding CSS on the Web." — [Reactiflux transcript](https://reactiflux.com/transcripts/nicolas-gallagher)
- Twitter Lite (2017) was built on RNW and "uses a small, fixed number of colors, font sizes, and lengths" — [blog.twitter.com](https://blog.twitter.com/2017/how-we-built-twitter-lite/); Lorber identifies Twitter's 2019 desktop app as the most significant atomic CSS-in-JS deployment, via RNW — [sebastienlorber.com](https://sebastienlorber.com/atomic-css-in-js)
- Gallagher later co-authored StyleX's launch post, which says StyleX is "aligned with the principles of encapsulation introduced by React Native's styling system." — [stylexjs.com](https://stylexjs.com/blog/introducing-stylex/)

### Inferences
- RN's "what was kept" is precisely the inherited-typography subset of CSS (and only within a `<Text>` subtree); everything box-related is non-inherited anyway in CSS, so RN effectively kept the one thing inheritance was for and removed the rest.
- The RNW page never uses the word "cascade"; the honest statement is that it removed source-order resolution and cross-component inheritance, not that it removed property inheritance within Text.

### Gaps
- No transcript of Gallagher's ReactEurope 2017 "The making of Twitter Lite" or React Rally talk was retrieved; I could not find a direct quote from him using the word "cascade".

## Key question 4: New CSS specs (@scope, @layer, container queries, @property, scroll-driven animations / timeline-scope, :has(), nesting) and what spec authors say

### Takeaway
The spec editors' own explainers describe @scope as native support for "what many authors are already doing" with CSS Modules/Vue/Styled-JSX — i.e. component ownership of a DOM fragment with a lower boundary ("donut scope") — while explicitly declining to solve full isolation; cascade layers are framed as an architectural tool for *why* a style wins, not for per-component scoping; container queries are explicitly motivated by component-based design systems. Scoping and ownership vocabulary now appears across unrelated specs (`timeline-scope`).

### Cited Findings

**@scope (CSS Cascading and Inheritance Level 6)**
- Editors: Elika J. Etemad / fantasai (Apple), Miriam E. Suzanne (Invited Expert), Tab Atkins Jr. (Google); Editor's Draft dated 28 April 2026. Scoping root is "the upper bound of the scope"; "The scoping limit elements, which act as the lower bounds."; scope proximity is a new cascade criterion placed after Specificity and before Order of Appearance: "the declaration with the fewest generational or sibling-element hops between the scoping root and the [subject]" wins; rules without a scoping root "are considered to have infinite proximity hops." — [drafts.csswg.org/css-cascade-6](https://drafts.csswg.org/css-cascade-6/)
- The spec explicitly acknowledges the tooling it is standardising: "Many existing tools implement 'scoped styles' by applying a unique class or attribute to every element"; an example uses `main-component` / `sub-component` scopes and a code comment refers to a "single file component." — [drafts.csswg.org/css-cascade-6](https://drafts.csswg.org/css-cascade-6/)
- Miriam Suzanne's explainer: "All CSS Selectors are global, matching against the entire DOM."; authors "rely on convoluted naming conventions (BEM) and JS tooling"; selectors "are not weighted by 'proximity' to the element being styled."; "There is no selector/specificity solution that accurately reflects what we want here"; "It would be useful for authors to express this DOM-fragment 'ownership' more clearly in native HTML/CSS."; Nicole Sullivan coined "donut" scope in 2011; components are described as an outer block, inner elements, and "donut holes" or "slots"; CSS Modules, Vue, Styled-JSX "often use a similar pattern"; the aim is "a native CSS approach for what many authors are already doing"; the primary use case is one in which "component-styles are 'locked-in' to avoid cross-contamination." — [css.oddbird.net/scope/explainer](https://css.oddbird.net/scope/explainer/)
- What @scope deliberately is not: full isolation is "mostly used for 'widgets'" and "We have not attempted to address that form of scope in this proposal"; scope "mostly acts as a protection from naming conflicts"; "Shadow-DOM is not designed for the common 'design system' approach". — [css.oddbird.net/scope/explainer](https://css.oddbird.net/scope/explainer/)
- Bramus (Chrome, 2023-10-04): @scope is "a way to select elements only within a subtree of your DOM"; "the scoping root which determines the upper boundary"; "a scoping limit which determines the lower boundary"; "This type of scoping–with an upper and lower boundary–is often referred to as a donut scope."; scoping proximity "comes in handy when nesting several variations of a component."; contrasted with Scoped CSS / Styled Components tools that "rewrite all your selectors"; "@scope limits the reach of the selectors. It doesn't offer style isolation." — [developer.chrome.com](https://developer.chrome.com/docs/css-ui/at-scope)

**Cascade layers (@layer)**
- Miriam Suzanne (2022-02-21): layers are "a CSS feature that allows us to define explicit contained layers of specificity"; "Cascade layers give CSS authors more direct control over the cascade"; "Cascade layers give us a way to slot third-party code into the cascade of any project"; "layers are intended as foundational building blocks of an entire CSS architecture"; she warns against the instinct to "create a layer for each component in a project" because "layers aren't particularly well designed for this type of scoped organization"; "Scopes describe what we are styling, while layers describe why we are styling". — [css-tricks.com/css-cascade-layers](https://css-tricks.com/css-cascade-layers/)
- Tooling adoption: Panda CSS emits `@layer utilities` etc. ("Generated styles use cascade layers, CSS variables, and modern selectors like `:where` and `:is`.") — [panda-css.com](https://panda-css.com/docs/overview/why-panda)

**Container queries**
- Una Kravets (web.dev, "The new responsive: Web design in a component-driven world", last updated 2021-05-19): viewport media queries "lack a lot of finesse"; components "still don't own their styles, and that doesn't work when our design systems are component-based and not page-based."; with container queries "the component itself owns its responsive information and sizes according to the container, not the viewport."; "Scoped styles allow for component-specific styling to avoid naming collisions." — [web.dev/articles/new-responsive](https://web.dev/articles/new-responsive)

**Scroll-driven animations / timeline-scope**
- MDN: "By default, a named timeline (i.e., declared using `scroll-timeline-name` or `view-timeline-name`) can only be set as the controlling timeline of a direct descendant element … This is the default 'scope' for the timeline."; `timeline-scope` on an ancestor "changes the scope of the timeline to include the targeted element and its descendants"; `all` "Sets the scope so that any timeline names set on the element or in its subtree are matched only by elements within the same subtree." — [MDN timeline-scope](https://developer.mozilla.org/en-US/docs/Web/CSS/timeline-scope)

**Custom properties as the component-parameter channel**
- Miriam Suzanne (2019-07-01): custom properties "can provide new ways to balance context and isolation in CSS patterns and components."; a custom property "acts similar to a parameter that can be passed into the `p` component."; "Custom properties inherit like any other property, but they don't have to be used where they are defined."; "If we don't want to expose the parameter for inheritance, we can define the variable with a default value:"; a fallback leaves a property "'free' to inherit a value from outside the component."; "Proximity is not part of the cascade, but it is part of CSS." — [smashingmagazine.com](https://www.smashingmagazine.com/2019/07/css-custom-properties-cascade/)
- Angular: "Custom properties inherit down the DOM tree" (listed as the thing that crosses emulated encapsulation) — [angular.dev](https://angular.dev/guide/components/styling)
- Shadow DOM: custom properties are the sanctioned "hooks" for outside theming — [web.dev](https://web.dev/articles/shadowdom-v1)

**Survey signal on new features**
- State of CSS 2024: `:has()` used by 72.9% (7,277 respondents), CSS Nesting used by 51.3%; `@scope` added to reading lists 1,611 times (Baseline: Limited Availability); `view-timeline` 1,563, `scroll-timeline` 1,557; `light-dark()` 1,377. No usage figure for `@layer` or container queries on the visible page. — [2024.stateofcss.com/features](https://2024.stateofcss.com/en-US/features/)

### Inferences
- Both the spec and its editor say @scope standardises the attribute/class-hashing pattern that CSS Modules, Vue and Svelte invented; the "lower boundary" exists precisely because components contain other components (slots/donut holes). That is a direct admission in the platform that the unit of styling is the component.
- Suzanne's warning not to create a layer per component, and her "scope = what, layer = why" formula, implies the intended modern architecture is: a few global layers (reset, tokens, defaults, third-party) feeding many component scopes — consistent with "only variables/tokens cascade".
- `timeline-scope` shows the same instinct in a non-styling spec: names are subtree-scoped by default and must be explicitly lifted to an ancestor.
- `@property` and `:has()` were not covered by fetched spec-author quotes; `:has()` is arguably a counter-signal (it lets a selector reach outward/upward), though @scope's proximity rule and StyleX's ban on complex selectors show frameworks constraining its use. Treat as inference, not sourced.

### Gaps
- I found no direct quotes from Tab Atkins or fantasai on scoping vs cascade; only their editor credits on the css-cascade-6 draft.
- The spec text I retrieved does not use the phrase "donut scope"; that phrase is in the OddBird explainer (attributing it to Nicole Sullivan, 2011) and Bramus's article.
- No spec-author quote retrieved for `@property` or `:has()` regarding component-local reasoning.
- The CSS-Tricks "Scope in CSS" URL returned 404; the OddBird explainer substitutes for it.
- No State of CSS usage figures found for `@layer`, container queries or `@property` (only reading-list counts for `@scope`).

### Takeaway
Large codebases that have written up their migrations (GitHub/Primer, Atlassian, Meta, Linear) all landed on build-time, locally-scoped component styles with theming carried solely by CSS custom properties; survey data show CSS Modules and Tailwind dominating, runtime CSS-in-JS receding, and "None" the most-selected CSS-in-JS answer in 2025.

- The 2025 survey's "None" majority within CSS-in-JS plus Tailwind at 51% suggests the industry's centre of gravity is now "utility/atomic + CSS Modules + variables", not runtime CSS-in-JS.

## Key question 6: Counter-evidence — what components still genuinely rely on cascading/inheritance

### Takeaway
Even the strictest systems keep three cross-component channels open: inherited text properties (font, color, line-height, direction), custom properties/tokens, and user-agent/user-level overrides (forced colors, color-scheme). Shadow DOM, RN/RNW and StyleX each state explicitly that inheritance crosses their boundary; what they remove is selector reach and order-dependent resolution, not inheritance.

### Cited Findings
- CSS inheritance definition: "inherited properties, which by default are set to the computed value of the parent element" vs "non-inherited properties, which by default are set to initial value of the property"; "A typical example of an inherited property is the `color` property."; "A typical example of a non-inherited property is the `border` property." — [MDN Inheritance](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_cascade/Inheritance)
- Shadow DOM does not stop inheritance: "Inheritable styles (background, color, font, line-height, etc.) continue to inherit in shadow DOM." (note: MDN/CSS classify `background` as non-inherited; Bidelman's list is loose on that item) and component authors expose "hooks (in the form of CSS custom properties)". — [web.dev/shadowdom-v1](https://web.dev/articles/shadowdom-v1)
- Shadow DOM and `direction`: "CSS inherits the `direction` property through the flattened tree, so an assigned element with no `dir` attribute of its own is rendered using the direction in effect at the slot"; `lang`/`dir` on a shadow root "are inherited from the shadow host instead." — [MDN Using shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)
- Angular emulated encapsulation: "global styles defined outside of a component may still affect elements inside a component"; "Custom properties inherit down the DOM tree". — [angular.dev](https://angular.dev/guide/components/styling)
- Vue: the child's root node "will be affected by both the parent's scoped CSS and the child's scoped CSS. This is by design". — [vuejs.org](https://vuejs.org/api/sfc-css-features.html)
- React Native: "React Native still has the concept of style inheritance, but limited to text subtrees." — [reactnative.dev](https://reactnative.dev/docs/text); RNW: "text style inheritance is only available within Text subtrees." — [necolas.github.io](https://necolas.github.io/react-native-web/docs/styling/)
- StyleX: inheritance "is the _only_ form of style-at-a-distance that StyleX allows". — [Thinking in StyleX](https://stylexjs.com/docs/learn/thinking-in-stylex/)
- Svelte's scoping relies on cascade mechanics (specificity bump of 0-1-0, `:where()`), i.e. it wins *through* the cascade rather than outside it. — [svelte.dev docs](https://svelte.dev/docs/svelte/scoped-styles)
- `currentColor`: "The `currentColor` keyword represents the value of an element's `color` property. This lets you use the `color` value on properties that do not receive it by default."; "If `currentColor` is used as the value of the `color` property, it instead takes its value from the inherited value of the `color` property." — [MDN color_value](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value#currentcolor_keyword)
- Forced colors (Windows High Contrast): the UA "enforces a user-chosen limited color palette on the page"; for `color`, `background-color`, `border-color`, `outline-color`, SVG `fill`/`stroke` and others "the values … are treated as if they have no author-level values specified … the values are instead forced by the browser at paint time."; `box-shadow` and `text-shadow` forced to `none`; `color-scheme` forced to `light dark`; escape hatch `forced-color-adjust: none`; "In general, web authors should not be using the `forced-colors` media feature to create a separate design". — [MDN forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors)
- Cascade layers exist because "we can't always control the selector specificity or importance of all the CSS" and because, per the CSS creators, "the user should have the last word" — [css-tricks.com/css-cascade-layers](https://css-tricks.com/css-cascade-layers/)
- Custom properties as the designed inheritance channel: "Custom properties inherit like any other property, but they don't have to be used where they are defined." — [smashingmagazine.com](https://www.smashingmagazine.com/2019/07/css-custom-properties-cascade/)
- Tooling that explicitly uses variables for the cross-boundary channel: Linaria ("Dynamic styles will be applied using CSS custom properties") — [github.com/callstack/linaria](https://github.com/callstack/linaria); vanilla-extract ("locally scoped classes, variables and themes") — [vanilla-extract.style](https://vanilla-extract.style/); Tailwind theme variables — [tailwindcss.com](https://tailwindcss.com/docs/styling-with-utility-classes); Panda `var(--colors-white)` tokens — [panda-css.com](https://panda-css.com/docs/overview/why-panda); GitHub's `@primer/css` theming variables — [github.blog](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)
- Survey: `prefers-color-scheme` used by 51.3% (7,393 respondents) in 2024; `light-dark()` on 1,377 reading lists. — [2024.stateofcss.com/features](https://2024.stateofcss.com/en-US/features/)

### Inferences
- The honest version of "almost nothing is worth cascading except variables" is: nothing *selector-driven* is worth cascading except tokens; property inheritance of typography/color/direction and the user/UA override layers (forced-colors, importance) remain, and every encapsulation system explicitly preserves them.
- `rem`-based sizing and `color-scheme` are inheritance-shaped dependencies on `:root`/`html` state; the sources above establish the mechanism (inherited properties, forced `color-scheme`) but no fetched source argues specifically about `rem` scaling in component systems.
- `currentColor` is a textbook case of a component deliberately *wanting* an inherited value (icon strokes following text color) and is used precisely because it crosses component boundaries without a selector.

### Gaps
- I did not retrieve a source explicitly discussing `font-size`/`rem` scaling or `color-scheme` inheritance in the context of component systems; those points are inferred from the general inheritance mechanism, not quoted.
- The MDN inheritance page's full list of inherited properties was truncated in the fetch; only `color` and `border` examples are quoted. Bidelman's "background, color, font, line-height" list includes `background`, which is not an inherited property in CSS; a blog author should not repeat that list uncritically.
- I could not locate the origin of the phrase "almost nothing is worth cascading except variables"; searches returned adjacent material (Suzanne on custom properties as parameters; Adactio's "A Tale of Two Buttons" defending the cascade) but not the quote itself. Treat it as the blog author's own thesis rather than a citation.
- Adactio (Jeremy Keith) "A Tale of Two Buttons" is a notable defence of embracing the cascade for consistency; not fetched, URL only: https://adactio.com/links/14276
